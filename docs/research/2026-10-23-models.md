另外两个**实测前必须知道**的坑（后面详述）：

* **Qwen3-ASR 的 `max_total_len` 在 Rust 绑定的默认值下被钳到 512**，会截断长音频；`max_new_tokens` 默认 128。必须显式设置。
* **Qwen3-ASR / Fun-ASR-Nano 是自回归 LLM 解码器**，单次识别的 KV cache 与生成 token 数成正比 —— 内存恒定的前提是 `max_new_tokens` 固定（这一点可以满足）。

### 排序建议（一句话）

1. **想要「可感知的准确率提升」且愿意加体积 → 整段模式换 FireRed ASR2 AED INT8**（中文绝对精度最高，Apache-2.0，同时覆盖流式与离线）。
2. **想要「不换模型但拿到热词能力 + 多语种」→ 整段模式换 Qwen3-ASR-0.6B INT8**（**热词才是本项目最大的准确率杠杆**，见 §3.1）。
3. **流式模式 → 换 X-ASR-zh-en INT8**（128 MB 带标点，比现在强且更小）。
4. **什么都不换** 也是合理选择：当前 SenseVoiceSmall INT8 在同表对比里 WenetSpeech net 5.73 / meeting 6.47 已经优于 Qwen3-ASR-0.6B（5.97 / 6.88），**纯换模型的 CER 增益是「混合」的，不是必然赢**。真正的确定性收益是「热词 + 拼音同音词替换 + 解码策略」这一组合（见同目录 `2026-10-23-decoding.md`）。

### 2.1 Qwen3-ASR-0.6B INT8 ★ 整段模式首选（配合热词）

#### 是什么

Qwen 官方 2026-01-29 发布的 Qwen3-ASR 系列（0.6B / 1.7B），基于 Qwen3-Omni 的音频理解能力，**一个模型同时做语种识别 + ASR**，支持 30 语种 + 22 种汉语方言，**离线/流式统一**。官方定位：「1.7B 达到开源 ASR 模型 SOTA，0.6B 是精度-效率折中」。

#### 在本项目怎么接

**支持性：✅ 可以直接加载。** crate `src/offline_asr.rs:325-352` 已有 `OfflineQwen3ASRModelConfig`；官方 Rust 示例 [rust-api-examples/examples/qwen3_asr.rs](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/rust-api-examples/examples/qwen3_asr.rs)。

```rust
// src-tauri/src/asr.rs —— 整段模式新增一个引擎分支
use sherpa_onnx::{
    OfflineQwen3ASRModelConfig, OfflineRecognizer, OfflineRecognizerConfig,
};

let mut config = OfflineRecognizerConfig::default();
config.model_config.qwen3_asr = OfflineQwen3ASRModelConfig {
    conv_frontend: Some(dir.join("conv_frontend.onnx").to_string_lossy().into()),
    encoder:       Some(dir.join("encoder.int8.onnx").to_string_lossy().into()),
    decoder:       Some(dir.join("decoder.int8.onnx").to_string_lossy().into()),
    tokenizer:     Some(dir.join("tokenizer").to_string_lossy().into()), // 注意：目录，不是文件
    // ⚠️ 必须显式给，不能用默认值 512（见下方「坑」）
    max_total_len: 1024,
    max_new_tokens: 512,
    // 可选：原生热词，ASCII 逗号分隔
    hotwords: Some("骨质疏松症,年年恋牛娘".into()),
    ..Default::default()
};
// ⚠️ Qwen3-ASR 不用 tokens.txt，必须给空串（官方示例就是这么写的）
config.model_config.tokens = Some(String::new());
config.model_config.provider = Some("cpu".into());
config.model_config.num_threads = threads();
```

**下载编排（`models.rs`）**：官方资产托管在 ModelScope `zengshuishui/Qwen3-ASR-onnx`，Hugging Face 上没有对应的 `csukuangfj/*` 仓库；GitHub release 的 `.tar.bz2` 也可以，但需要解包。按项目现有 `Asset { name, path, bytes, sha256 }` 结构，把 6 个文件（conv_frontend / encoder / decoder / tokenizer×3）登记为独立 asset 即可，**镜像策略要改成 ModelScope 优先**（国内 ModelScope 比 HF 稳）。

**必须知道的三个坑：**

1. **`max_total_len` 默认 512 会截断长音频。** 上游实现 `sherpa-onnx/csrc/offline-recognizer-qwen3-asr-impl.cc`：
   ```cpp
   const int32_t model_max_len = model_->GetMaxTotalLen();          // 来自 decoder ONNX 的 KV cache 维度
   const int32_t max_total_len_opt = stream->GetOptionInt("max_total_len", qwen3_config.max_total_len);
   if (max_total_len_opt > 0) max_seq_len = std::min(model_max_len, max_total_len_opt);
   ```
   Rust 绑定默认 `max_total_len = 512`（`src/offline_asr.rs:344`），C API 同样是 `SHERPA_ONNX_OR(..., 512)`（`c-api/c-api.cc:639-640`）—— **默认会用 min(model_max_len, 512)**，即使模型本身支持更长上下文也会被钳住。
   音频 token 速率：`kQwen3ChunkSize = 100`（ms）→ **每秒 10 个音频 token**，再减去 prompt 前后缀与 `max_new_tokens` 预算。**单次可识别音频长度的实际上限官方未公布（未证实）**，必须实测；官方示例用 512/512，也有一处用 1024/1024（[pretrained.html](https://k2-fsa.github.io/sherpa/onnx/qwen3-asr/pretrained.html)）。
   本项目现状是「VAD 分句，每句一次识别；超过 90 秒才切 30 秒窗口」——**若换 Qwen3-ASR，必须实测单句上限并相应下调 `MAX_SINGLE_SHOT_SECONDS`**，否则长句会被静默截断（上游会打 warning 并给出 `Qwen3LogMaxTotalLenSuggestions`）。

2. **`feat_config.feature_dim` 不用改。** `kQwen3MelDim = 128`（上游常量），但 Qwen3-ASR 的 stream 是用 `WhisperTag` 建的（`offline-recognizer-qwen3-asr-impl.cc:428-430` → `offline-stream.cc:72` `Impl(WhisperTag tag)`，`opts_.mel_opts.num_bins = tag.dim`），**模型自己接管了特征维度**，Rust 侧保持默认 80 即可（官方示例的 dump 里也是 `feature_dim=80`）。

3. **热词格式是 ASCII 逗号分隔**，且被放进 chat template 的 system 段（上游 `Qwen3FormatHotwordsForPrompt`）。官方示例热词：`骨质疏松症患者,咬死山前,紫色柿子树,年年恋牛娘,灰黑灰化肥,走出香港`。

#### 预期收益

* **CER 层面**：见上表 —— 中文大致打平、英文与口音明显更好。**不要把它当成「中文大幅提准」的方案。**
* **热词层面（这才是重点）**：SenseVoice **完全不支持热词**（同目录 `2026-10-23-decoding.md` §2.1 已验证），Qwen3-ASR 原生支持。该调研实测热词把项目自有测试集的专名命中率从 **48/140 → 94/140**，真实录音 **6/30 → 22/30**。**如果把引擎换成 Qwen3-ASR，这条收益就从「不可行」变成「开箱即用」。**

#### 代价

* 体积：239 MB → 约 1 GB（下载量 ×4）。
* CPU：官方 CPU RTF **0.077–0.168**（2–3 线程；出处 [qwen3-asr/pretrained.html](https://k2-fsa.github.io/sherpa/onnx/qwen3-asr/pretrained.html) 的 `Real time factor (RTF)` 输出），与 SenseVoice 的 0.09–0.11 基本同档，**不构成障碍**。
* 内存：自回归解码，KV cache 随 `max_total_len` 线性增长。**只要 `max_total_len` 固定，内存就是恒定的**（约束可满足）。但比 SenseVoice 的 encoder-only 架构多一份 KV cache。

#### 风险

* 长音频截断（上面坑 1）——**这是最大的落地风险，必须先实测**。
* `max_new_tokens` 不足会导致输出被截断（上游提示「increase --qwen3-asr-max-new-tokens if generation is truncated」）。
* ModelScope 托管，国内下载路径与项目现有 HF→hf-mirror 策略不同，需要改 `models.rs` 的源列表。
* 上游有「退化尾部修剪」「循环幻觉窗口」等特殊逻辑（`TrimDegenerateTail`、`kQwen3LoopWindow=64`），说明**存在已知的重复输出问题**，需要用项目自己的长录音回归验证。

### 2.2 FireRed ASR2 AED / CTC INT8 ★ 中文绝对精度最高

#### 是什么

FireRed 团队的 FireRedASR2 系列（arXiv:2603.10420，*FireRedASR2S: A State-of-the-Art Industrial-Grade All-in-One ASR System*）。**AED 成员**是 Conformer encoder + Transformer decoder 的注意力编解码器，1.1B 参数，**中英双语（含 code-switching）**，无语言标志位。

sherpa-onnx 侧有两个包：
* `sherpa-onnx-fire-red-asr2-zh_en-int8-2026-02-26`（AED，799.7 MB）→ `OfflineFireRedAsrModelConfig`
* `sherpa-onnx-fire-red-asr2-ctc-zh_en-int8-2026-02-25`（CTC，496.4 MB）→ `OfflineFireRedAsrCtcModelConfig`

**两个都支持流式**（sherpa-onnx 文档页的 FireRedAsr 章节有「Real-time/Streaming Speech recognition from a microphone with VAD」示例）。

#### 一手来源

- 论文：[arXiv:2603.10420](https://arxiv.org/abs/2603.10420)（Table 2）
- 权重：[FireRedTeam/FireRedASR2-AED](https://huggingface.co/FireRedTeam/FireRedASR2-AED)
- sherpa-onnx 文档：[k2-fsa.github.io/sherpa/onnx/FireRedAsr](https://k2-fsa.github.io/sherpa/onnx/FireRedAsr/index.html)
- crate：[`src/offline_asr.rs:143-155`](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/rust-api-examples/examples/fire_red_asr_ctc.rs)（AED）与 `:311-321`（CTC）

#### 中文 CER（出处：arXiv:2603.10420 Table 2，经 [OpenASR/firered-aed-l-v2 model card](https://huggingface.co/OpenASR/firered-aed-l-v2) 转述）

#### 代价

* 体积 800 MB（比现状 239 MB 大 3.3×）。

* 无热词接口 —— 对本项目而言**这可能是致命的**，因为热词是最大的准确率杠杆（SenseVoice 同样没有热词，所以至少不倒退）。
* 论文与官方 card 的数字来自不同训练批次，跨表比较要小心（OpenASR card 自己也提醒不要把 v1 的 3.18%/0.55% 和 v2 混用）。

### 2.3 X-ASR-zh-en INT8 ★ 流式模式首选

#### 是什么

[Gilgamesh-J/X-ASR](https://github.com/Gilgamesh-J/X-ASR) 系列，基于 icefall/k2 框架，**Zipformer transducer** 架构，**约 100 万小时**训练数据，「**离线-流式统一**」：同一套权重既能做离线整段解码，也能做真流式解码。提供 **160 / 480 / 960 / 1920 ms** 四种流式 chunk，**支持标点与大小写**。参数量 **0.16B**。

sherpa-onnx 侧有 8 个预编译包（非流式 4 个 + 流式 chunk 4 个），**全部有 INT8**。

#### 一手来源

- Model card：[GilgameshWind/X-ASR-zh-en](https://huggingface.co/GilgameshWind/X-ASR-zh-en)
- 项目仓库：[Gilgamesh-J/X-ASR](https://github.com/Gilgamesh-J/X-ASR)
- sherpa-onnx 导出脚本（v1.13.8 内）：`scripts/zipformer-transducer/x-asr/export-{streaming,non-streaming}.sh`、`test_onnx_{streaming,non_streaming}.py`、`.github/workflows/export-x-asr.yaml`
- 打包脚本：[upload-models.yaml](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/.github/workflows/upload-models.yaml) L31-110

#### 中文 CER / WER（出处：X-ASR 官方 model card「Evaluation」，greedy search）

| 模式 | chunk | LibriSpeech clean | other | GigaSpeech | WenetSpeech net | meeting |
|---|---|---|---|---|---|---|
| 流式 | 160 ms | 3.91 | 10.17 | 10.97 | 12.04 | 9.45 |
| 流式 | 480 ms | 3.14 | 7.57 | 9.77 | 9.31 | 7.38 |
| 流式 | 960 ms | 3.12 | 7.22 | 9.62 | 8.84 | 6.96 |

> 对比当前模型的同表数据：**SenseVoice-small 234M = 3.16 / 7.21 / 11.24 / 5.73 / 6.47**。即：X-ASR 在英文/口音上赢，**在 WenetSpeech 中文上略输**（5.96 vs 5.73）。但 X-ASR 是**流式**模型 —— 而当前流式模型 `streaming-zipformer-zh-int8-2025-06-30` 的官方中文 CER **未证实**（sherpa-onnx 文档页只给 RTF，不给 CER）。

#### 在本项目怎么接

**注意三个必填字段与现状不同**（现状是 `model_type=""`、`modeling_unit="cjkchar"`、`bpe_vocab=""`）：

```rust
// 流式模式（OnlineTransducerModelConfig）
use sherpa_onnx::{OnlineRecognizerConfig, OnlineTransducerModelConfig};

let mut config = OnlineRecognizerConfig::default();
config.model_config.transducer = OnlineTransducerModelConfig {
    encoder: Some(dir.join("encoder-1920ms.int8.onnx").to_string_lossy().into()),
    decoder: Some(dir.join("decoder-1920ms.onnx").to_string_lossy().into()),
    joiner:  Some(dir.join("joiner-1920ms.int8.onnx").to_string_lossy().into()),

config.model_config.tokens = Some(dir.join("tokens.txt").to_string_lossy().into());

config.model_config.modeling_unit = Some("bpe".into());
config.model_config.bpe_vocab = Some(dir.join("bpe.model").to_string_lossy().into());

config.model_config.provider = Some("cpu".into());
config.model_config.num_threads = threads();
```

`model_type = "zipformer2"` 有**硬证据**：包内 `test_onnx.py` 从 encoder ONNX 的 metadata 读取并断言
```python
model_type = encoder_meta["model_type"]
assert model_type == "zipformer2", model_type
```
（`scripts/zipformer-transducer/x-asr/test_onnx_streaming.py` L180-181；官方 X-ASR 部署脚本也用 `--model-type zipformer2`）。

**离线模式复用同一套权重**（官方 model card 明确是「offline-streaming unified」）：
```rust
config.model_config.transducer = OfflineTransducerModelConfig { encoder, decoder, joiner };
config.model_config.model_type = Some("zipformer2".into());
config.model_config.modeling_unit = Some("bpe".into());
config.model_config.bpe_vocab = Some(bpe_model);
config.model_config.tokens = Some(tokens);
```

**chunk 尺寸与项目现状的对应关系**：项目现在按 **200 ms（3200 样本）分片**喂流式解码器。X-ASR 的 chunk 是模型内建的（160/480/960/1920 ms），**分片间隔必须 ≥ chunk 尺寸**。建议选 **480 ms**（WenetSpeech net 9.31 / meeting 7.38，比 160 ms 的 12.04 好很多，而延迟只比 960 ms 高一点），并把项目的喂数节奏从 200 ms 改成 480 ms —— **注意 sherpa-onnx 的特征缓冲约束（见 AGENTS.md 里的踩坑记录）：必须只在 `is_ready()` 为真时 `decode()`，否则会 abort。**

#### 预期收益

* 流式模式**自带标点与大小写** —— 当前流式模式标点靠单独的 CT-Transformer（294 MB）补，且「只用于流式模式给句子补标点」。X-ASR 把这部分开销去掉了。
* 中文 + 英文双语（当前流式模型只有中文，**选粤/日/韩时前端会强制切回非流式** —— X-ASR 可以缓解这个限制）。
* 离线/流式**同一套权重**，可只下载一份。

#### 代价

* 需要把流式喂数节奏从 200 ms 改到 480/960 ms。
* `modeling_unit` 从 `cjkchar` 改成 `bpe`，且多一个 `bpe.model` 文件要下载与校验。
* 离线模式下，X-ASR 的中文 CER 略输 SenseVoice（5.96 vs 5.73）—— **所以离线模式不建议换 X-ASR，只建议流式模式换**。

#### 风险

* **技术报告「Coming Soon」** —— 所有评测数字都是作者自测，未经第三方复现。
* 逐字（cjkchar）与 BPE 词表的差异会改变 `joinText()` 的分词行为与 `asr::join_segments()` 的空格规则（AGENTS.md 记录：中日韩之间直接连、其余加空格）—— **BPE 输出可能带来不必要的空格**，需要复核。
* `bpe_vocab` / `modeling_unit` 配错会**静默出乱码或空结果**，不像 SenseVoice 那样报错明显。

## 3. 排序与取舍（回答「哪个最可能带来可感知的准确率提升」）

### 3.1 先说结论：**纯换模型的 CER 增益是混合的，真正的杠杆是「热词」**

在唯一一份**把 SenseVoice 与所有候选放在同一评测协议下的表格**里（[X-ASR model card](https://huggingface.co/GilgameshWind/X-ASR-zh-en)，greedy search）：

| 模型 | AVG（5 个基准） | WenetSpeech net | WenetSpeech meeting |
|---|---|---|---|
| Qwen3-ASR 1.7B | 4.882 | 5.29 | 5.46 |
| Qwen3-ASR 0.6B | 5.702 | 5.97 | 6.88 |
| X-ASR-zh-en (offline) | 6.036 | 5.83 | 7.06 |
| **SenseVoice-small（现状）** | 6.762 | **5.73** | **6.47** |

**在中文两项上，当前 SenseVoice 反而略优于 Qwen3-ASR-0.6B 与 X-ASR。** 所以「换个更强的模型就能提中文准确率」这个前提**在现有公开数据下不成立**。

真正确定性更高的收益来自三处：

1. **热词（最高杠杆）** —— 同目录 `2026-10-23-decoding.md` 实测：项目自有测试集专名命中率 **48/140 → 94/140**，真实录音 **6/30 → 22/30**。但 **SenseVoice 无热词接口**。Qwen3-ASR / Fun-ASR-Nano **原生支持热词**（`OfflineQwen3ASRModelConfig.hotwords` / `OfflineFunASRNanoModelConfig.hotwords`），**换过去等于把这条最高 ROI 的手段解锁**。
2. **方言与多语** —— 项目已有粤/日/韩语言选项，但 SenseVoice 的粤/日/韩能力有限；Qwen3-ASR（30 语种 + 22 汉字方言）、Fun-ASR-Nano（7 方言 + 26 口音）、FireRed ASR2（20+ 方言）都更强。
3. **标点自带** —— X-ASR 流式版自带标点，可省掉 294 MB 的 CT-Transformer。

### 3.2 分模式排序

**整段模式（离线）：**

| 排名 | 方案 | 理由 | 代价 | 风险 |
|---|---|---|---|---|
| 1 | **FireRed ASR2 AED INT8** | 中文绝对精度最高（aishell1 0.57%、WenetSpeech ~4.95%），方言覆盖最广，双语 | 800 MB；无热词；无自带标点 | 标点需另配；无热词 |
| 2 | **Qwen3-ASR-0.6B INT8** | 解锁热词 + 52 语种；英文/口音大幅提升 | 838 MB | **`max_total_len` 截断（必须实测）**；长文本慢 |
| 3 | **Fun-ASR-Nano INT8** | 热词 + `language`/`itn` 双开关，语义与项目现有设置一一对应 | 803 MB；RTF 慢 1.6–1.9× | `language` 取值是汉字；`max_new_tokens` 截断 |
| 4 | **X-ASR-zh-en INT8（离线解码）** | 体积最小（167 MiB）、离线流式同权重 | 离线中文略输现状 | `modeling_unit="bpe"` 改动大 |
| 5 | **不动（SenseVoice 2024-07-17）** | 中文 WenetSpeech 仍是最好的一档；体积最小；已验证 | 无热词 | — |

**流式模式（在线）：**

| 排名 | 方案 | 理由 | 代价 | 风险 |
|---|---|---|---|---|
| 1 | **X-ASR-zh-en INT8（1920ms 或 480ms chunk）** | 唯一带官方评测的流式中文模型；**自带标点**；中英双语（解除「非中文强制切回离线」的限制）；体积与现状持平 | 喂数节奏要从 200 ms 改到 chunk 大小；`modeling_unit` 改 bpe | 技术报告未发布；BPE 输出与 `joinText()` 空格规则可能冲突 |
| 2 | **FireRed ASR2 INT8（AED 或 CTC）** | 中文精度最高且支持流式 | 800/496 MB | 标点仍需另配 |
| 3 | **不动（streaming-zipformer-zh-int8-2025-06-30）** | 已调优（200 ms 分片、300 ms 尾部补静音、VAD 门控） | — | 官方中文 CER 未证实 |

### 3.3 取舍总结

* **想要最小改动 + 最大确定性** → **先不动模型**，把同目录 `2026-10-23-decoding.md` 的热词/同音词替换/解码策略做完（这些在 SenseVoice 上就能生效，且实测收益最大）。
* **愿意加体积换能力** → 整段换 **Qwen3-ASR-0.6B**（拿热词 + 多语），流式换 **X-ASR**（拿标点 + 中英双语）。**必须先做 `max_total_len` 截断的实测**。
* **只追求中文绝对精度** → 整段换 **FireRed ASR2 AED**，流式也可一起换，但要准备好加标点模型。
* **本项目的三条硬约束如何被满足**：
  * *本地离线* → 全部候选都是纯 ONNX，sherpa-onnx C++ 原生支持，**不需要 Python 运行时**（Fun-ASR 官方另有 llama.cpp/GGUF 路线，但那是另一套运行时，不影响本项目）。
  * *单次下载 + sha256 固定* → 全部候选都有 sherpa-onnx 官方预编译包 + 固定 HF/ModelScope commit，可沿用项目现有 `Asset { name, path, bytes, sha256 }` 机制。**注意 Qwen3-ASR 与 Fun-ASR-Nano 只在 ModelScope 上有 sherpa-onnx 导出**（`zengshuishui/*`），HF 上没有对应仓库，镜像策略要调整。
  * *内存恒定* → 纯 encoder-decoder（SenseVoice / X-ASR / FireRed AED / Paraformer）天然恒定；自回归 LLM（Qwen3-ASR / Fun-ASR-Nano）需要把 `max_total_len` / `max_new_tokens` **固定写死**才能恒定 —— 可以做到，但要在配置里显式设，不能依赖默认值。

## 不建议做的（及原因）

### 4.1 Qwen3-Omni / Qwen-Audio / 「Omni-ASR」——1.13.8 完全不支持

* **依据一（crate 源码）**：`~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/sherpa-onnx-1.13.8/src/` 下 **16 个文件里 `omni` 的命中数为 0**，唯一的 8 处命中全在 `offline_asr.rs`，且全部是 **`OfflineOmnilingualAsrCtcModelConfig`**（Meta 的 Omnilingual ASR，CTC）—— 与 Qwen-Omni 无关。
* **依据二（上游打包脚本）**：v1.13.8 的 `.github/workflows/upload-models.yaml` 中没有任何 `qwen-omni` / `qwen-audio` 资产。
* **依据三（推理成本）**：Qwen3-Omni 是全模态大模型，官方定位就是需要 GPU 实时交互；即使强行导出 ONNX，CPU 上跑一个多模态 LLM 与「实时转写」的目标直接冲突。
* **结论**：**不可行**。想用 Qwen3 家族的 ASR，走 **Qwen3-ASR-0.6B**（§2.1），那是有 sherpa-onnx 原生支持的。

### 4.2 FireRed ASR **v1**（fp16，1976.9 MiB）

* 依据：sherpa-onnx 只提供了 `sherpa-onnx-fire-red-asr-large-zh_en-fp16-2025-02-16`（**fp16**，解包 encoder.fp16 1480.8 MB + decoder.fp16 752.3 MB ≈ 2.2 GB）。**没有官方 INT8 版本**。
* 体积远超项目可接受范围；v2（ASR2）已有 INT8，**直接用 v2**。

### 4.3 NeMo / Citrinet / Parakeet / Canary / MedASR / GigaAM —— 语言不匹配

* 依据：`asr-models` release 里这一族的包名全部带 `-en`（`nemo-ctc-en-citrinet-512`、`nemo-parakeet-tdt-0.6b-v2`、`nemo-canary-180m-flash-en-es-de-fr`、`medasr-ctc-en`、`nemo-transducer-giga-am-russian`）—— **没有一个含中文**。「CIT」= Citrinet，也是英文。
* **不可行**（与中文需求无关）。

### 4.4 Whisper large-v3 / large-v3-turbo / distil 系列 —— 中文更差 + 体积更大

* 依据：Qwen3-ASR 与 Fun-ASR 官方评测表里 Whisper-large-v3 的中文数字全面落后（见 §2.8 表格）；large-v3 INT8 解包 1.7 GB；**large-v3-turbo 的中文 CER 官方未以文字公布（未证实）**，不能假设持平。
* **不可行**（对本项目的中文目标是负收益）。

### 4.5 SenseVoice 2025-09-09 —— 粤语微调 + 丢标点

* 依据：sherpa-onnx 官方文档「**This model does not support punctuations**」，且它由 2024-07-17 用 21.8k 小时粤语音频微调而来。
* 本项目整段模式依赖 SenseVoice 的 ITN 自带标点（AGENTS.md 明确「不要再给整段结果再套一遍标点模型，否则会叠成『。。』」）。换 2025-09-09 → **既丢标点又不能套标点模型**。**负收益。**

### 4.6 Dolphin / Omnilingual ASR —— 中文无数据 + CTC 无标点

* 依据：官方 README 未给出中文 CER（**未证实**）；两者都是 CTC 架构，无标点、无 ITN。
* **不可行 / 收益不可证**。

### 4.7 Cohere Transcribe —— 体积最大且中文未证实

* 依据：1621.0 MB（现有 SenseVoice 的 6.8×），14 语种官方未公布中文 CER。
* **不可行**。

### 4.8 paraformer-zh-2025-10-07 —— 只支持川渝方言

* 依据：sherpa-onnx 文档「It is fine-tuned on csukuangfj/sherpa-onnx-paraformer-zh-2023-03-28 with 10k hours」+ 标题即「四川话、重庆话、川渝方言」。
* 只有在明确要做川渝方言时才考虑。

### 4.9 一切需要 GPU / Python 运行时 / 大体积的方案

* 需要 Python 运行时：Fun-ASR 的 `funasr` + PyTorch 路线、Qwen3-ASR 的 `qwen-asr` + transformers/vLLM 路线 —— **本项目是 Rust + Tauri，不引入 Python**。sherpa-onnx 的纯 C++ 路线是唯一可行路径。
* 需要 GPU：Qwen3-Omni、Fun-ASR 的 vLLM 批量路径、FireRed 的 OpenASR fp16 高吞吐路径 —— 全部排除。
* 大体积：Whisper medium（1841.9 MB）、Cohere（1621.0 MB）、FireRed v1 fp16（1976.9 MB）、Paraformer trilingual（1010.4 MB）—— 全部排除。

### 4.10 「升级 sherpa-onnx crate」不是必要条件

* 依据：v1.13.8（2026-09-10）已经包含本次全部候选所需的结构体（`OfflineQwen3ASRModelConfig` / `OfflineFunASRNanoModelConfig` / `OfflineFireRedAsrModelConfig` / `OfflineFireRedAsrCtcModelConfig` / `OfflineTransducerModelConfig` / `OfflineZipformerCtcModelConfig` / `OfflineWenetCtcModelConfig` / `OfflineParaformerModelConfig` / `OfflineDolphinModelConfig` / `OfflineOmnilingualAsrCtcModelConfig` / `OfflineCohereTranscribeModelConfig`）。
* **建议不升级 crate**：AGENTS.md 记录了「首次编译 `sherpa-onnx-sys` 会从 GitHub Releases 拉预编译静态库，GitHub 不通时要用 `SHERPA_ONNX_ARCHIVE_DIR`」—— 换 crate 版本会重蹈这个坑。**在 1.13.8 内换模型即可。**
