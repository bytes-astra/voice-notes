### 0. 先纠正三个前提

调研中发现提问里的三个假设与**本地 crate 源码**不符，先纠正，否则后面的建议会写错字段名：

| 提问里的假设 | 实际情况（一手来源） |
|---|---|
| 「`FsmnVadModelConfig` 是否存在」 | **不存在**。sherpa-onnx 1.13.8 的 `VadModelConfig` 只有两个变体字段：`silero_vad: SileroVadModelConfig` 和 `ten_vad: TenVadModelConfig`（`sherpa-onnx-1.13.8/src/vad.rs:64-71`）。C API 同构：`sherpa-onnx-sys-1.13.8/src/vad.rs:24-31`。上游 master 的 `sherpa-onnx/csrc/vad-model-config.h` 也只有这两个。**FSMN-VAD 不在 sherpa-onnx 里。** |
| 「Tencent/webrtcvad 是否支持」 | Tencent 的 **TEN-VAD 支持**（`TenVadModelConfig`，`src/vad.rs:38-45`）；**webrtcvad 不支持**（Silero 官方 wiki 把 WebRTC VAD 当作对比基线，不是候选）。 |
| 「`speech_pad_ms` 参数」 | **sherpa-onnx 1.13.8 没有这个字段**（Rust 与 C API 都没有）。sherpa 用另一种方式实现「前后留白」：见下面 §2.2。`speech_pad_ms` 是 Silero **官方 Python** `get_speech_timestamps()` 的参数（默认 30 ms）。 |

另外两个必须知道的**上游硬编码**（`v1.13.8` tag 与 `master` 内容一致，已逐行比对）：

* `sherpa-onnx/csrc/voice-activity-detector.cc:228-229`
  ```cpp
  float new_min_silence_duration_s_ = 0.1;
  float new_threshold_ = 0.90;
  ```
  这就是项目注释里说的「min_silence 0.5→0.1 / threshold 0.5→0.9」——**它们是 sherpa 写死的，配置里改不了**。
* `sherpa-onnx/csrc/circular-buffer.cc:106-126`：`Push` 溢出时**自动扩容一倍并整段拷贝**，只打一行 `Overflow! ... (Original data is copied. No data loss!)`。
  → 所以「VAD 缓冲给 60 秒」**不是硬上限**，只是一次扩容的起点；超长句会让 CircularBuffer 反复翻倍（每次 O(n) 拷贝）。

| ROC-AUC · Multi-Domain Validation | 0.73 | 0.91 | **0.96** | 0.93 |
| 31.25 ms 帧准确率 · Multi-Domain | 0.74 | 0.85 | **0.91** | 0.87 |

**延迟（官方 wiki [Performance Metrics](https://github.com/snakers4/silero-vad/wiki/Performance-Metrics)，AMD 3960X 单线程）**

| 模型 | 每 31.25 ms 耗时 | 实时倍率 |
|---|---|---|

→ v5 既更准也更快。对本项目（16 kHz、512 样本/窗）VAD 推理成本可忽略（≈1.2% 单核）。

**可行性核对（关键：不用改一行 Rust 代码）**

sherpa 是**按 ONNX 张量签名自动区分 v4/v5** 的，`sherpa-onnx/csrc/silero-vad-model.cc`（v1.13.8 tag 第 205-225 行）：

```cpp
if ((input_names_.size() == 4 && output_names_.size() == 3) || IsExportedByK2Fsa()) {
  is_v5_ = false;
} else if (input_names_.size() == 3 && output_names_.size() == 2) {
  is_v5_ = true;
  window_overlap_ = 64;                       // 64 for 16kHz
  if (config_.silero_vad.window_size != 512) { // ← 16 kHz 下必须 512
    SHERPA_ONNX_LOGE("For silero_vad  v5, we require window_size to be 512 for 16kHz");
    SHERPA_ONNX_EXIT(-1);
  }
} else {
  SHERPA_ONNX_LOGE("Unsupported silero vad model");
  SHERPA_ONNX_EXIT(-1);
}
```

* 已用 `strings` 核对两个模型的实际张量名：
  * v4（现状）：`input` / `output`（上游 v4 的完整签名是 `input, sr, h, c` → `output, hn, cn`，见 `CheckV4()`）→ 4 入 3 出 → 命中 `is_v5_ = false` 分支 ✅
  * v5：`input` / `state` / `sr` → `output` / `stateN`（3 入 2 出）→ 命中 `is_v5_ = true` 分支 ✅
* 项目 `asr.rs:16` 的 `VAD_WINDOW = 512` **已经满足 v5 的硬性要求** ✅
* v5 的内部 `WindowSize()` = `512 + 64 = 576`，但 `VoiceActivityDetector::AcceptWaveform` 自己会攒够窗口
  （`voice-activity-detector.cc:80-95`），项目喂 512 样本一片是安全的 ✅
* `sample_rate` 必须是 16000（`silero-vad-model.cc` 里 `Expected sample rate 16000` 否则 `exit(-1)`）→ 项目本来就是 16 kHz ✅

**下载可得性（关键：能不能沿用「镜像优先 + 固定 commit + sha256」）**

✅ **可以，而且和现有资产同一个 HF commit**：

```
https://huggingface.co/csukuangfj/vad/resolve/fba88cd2e921609e7675c3aaf51e0b9b295da4bc/silero_vad_v5.onnx
```

#### 1.3 TEN-VAD：可以用，但性价比不如 v5

* Rust 侧确实有：`TenVadModelConfig`（`src/vad.rs:38-45`），字段与 Silero 完全同构。

→ **结论**：只在你确实需要换模型时考虑；升级到 v5 的性价比明显更高（质量更好、速度更快、有 HF 镜像、许可更宽松）。

#### 1.4 FSMN-VAD / Silero v6 / webrtcvad：为什么不可行

* **FSMN-VAD**：SenseVoice 官方 pipeline 用的是它（FunASR 的 `vad_model="fsmn-vad"`，见 [SenseVoice README](https://github.com/FunAudioLLM/SenseVoice)），
  但 **sherpa-onnx 的 C/Rust API 都没有它**。可达路径只有两条：装 FunASR(Python) 或换 llama.cpp 的 `llama-funasr-sensevoice`（带 `fsmn-vad.gguf`）——
  两者都等于换掉整个推理栈，与「本地桌面应用、Tauri + Rust」的目标冲突。
* **Silero v6**：Silero 版本历史（[wiki](https://github.com/snakers4/silero-vad/wiki/Version-history-and-Available-Models)）记 v6.0 = 2025-08-25、v6.2 = 2025-12-10，
  质量也确实最好（Multi-Domain ROC-AUC 0.97、ESC-50 准确率 0.87）。**但是**：
  1. 已实测 `snakers4/silero-vad` 的 `v6.0` / `v6.2` / `master` 三个 ref 的 `files/` 目录里**只有 `silero_logo.jpg`，没有 ONNX**（下载到的是 GitHub 的 HTML 错误页）；
  2. sherpa-onnx 官方文档只写「support both silero-vad v4 and v5」，`silero-vad-model.cc` 也只分支 v4(4 入 3 出)/v5(3 入 2 出) 两种签名，
     其它签名会走到 `SHERPA_ONNX_LOGE("Unsupported silero vad model"); SHERPA_ONNX_EXIT(-1);` → **进程 abort**。
  → 在 sherpa 支持 v6 之前，**绝不能把 v6 文件塞进 `silero_vad.onnx`**。
* **webrtcvad**：Silero 官方 wiki 把它列为对比基线（“pretty poor at separating speech from noise”，ROC-AUC 0.73），sherpa-onnx 也不支持。

### 2. VAD 参数调优

#### 2.1 五个参数在 sherpa 里的确切语义

`sherpa-onnx/csrc/silero-vad-model.cc` 的 `IsSpeech()`（v1.13.8 tag 第 100-175 行）是一台状态机：

| 参数 | 字段（`SileroVadModelConfig`） | sherpa 里的作用 | 调大 | 调小 |
|---|---|---|---|---|
| `threshold` | `threshold: f32`（`src/vad.rs:16`） | 帧级语音概率阈值；`prob > threshold` 才算语音 | 更保守：噪声误报少，但轻声/句尾易被判成静音 → **漏字** | 更激进：噪声也进句子 → 句子带噪 |
| `min_silence_duration` | `min_silence_duration: f32`（秒） | 静音持续多久才切句；同时决定**句子尾部保留多少静音**（`end = Tail - MinSilenceDurationSamples`） | 句子更长、更多粘连 → **「拖太长带静音」** | 切得更碎；可能切开词中间 |
| `min_speech_duration` | `min_speech_duration: f32`（秒） | 短于此的语音段直接丢弃；**同时决定句首留白长度**（见 §2.2） | 更长的句首留白（保字头），但「嗯」「好」这类短应答会被整段丢掉 | 短句能保留，但句首留白变短 → **易切字头** |
| `max_speech_duration` | `max_speech_duration: f32`（秒） | **不是硬切**：超过后 sherpa 把阈值调成 0.9、min_silence 调成 0.1，逼 VAD 找静音 | 收紧更晚触发 → 句子可以拖很久 | 收紧更早触发 → 更容易切碎（且收紧参数不可调） |
| `speech_pad_ms` | **不存在于 sherpa-onnx 1.13.8** | —— | —— | —— |

另有 `neg_threshold`（**C++ 里有、1.13.8 的 Rust 绑定里没有**）：
`sherpa-onnx/csrc/silero-vad-model-config.h:34-39` 默认 `-1` → 实际取 `max(threshold - 0.15, 0.01)`，
用于「语音→静音」的迟滞判断，是 sherpa 不会在句中一顿一顿地抖着切的主要机制。
Rust 侧 `SileroVadModelConfig` 只有 6 个字段（`model / threshold / min_silence_duration / min_speech_duration / window_size / max_speech_duration`），
**`neg_threshold` 暴露不出来**（除非升级到暴露该字段的 crate 版本，或自己走 C API）。

#### 2.2 「切掉字头」在整段模式里到底由什么决定（重要）

sherpa 的句子起点在 `sherpa-onnx/csrc/voice-activity-detector.cc:97`（v1.13.8 tag 同）：

```cpp
start_ = std::max(buffer_.Tail() - 2 * model_->WindowSize() -
                          model_->MinSpeechDurationSamples(),
                  buffer_.Head());
```

即 **句首留白 = 2 × 窗长 + min_speech_duration**：

| 模型 | 2×WindowSize | min_speech 0.25 s | **句首留白** |
|---|---|---|---|
| v4 | 2×512 = 64 ms | 250 ms | **≈ 314 ms** |
| v5 | 2×576 = 72 ms | 250 ms | ≈ 322 ms |

→ **整段模式其实已经自带 ~0.3 s 的句首留白**，比 Silero 官方 `speech_pad_ms=30` 宽 10 倍。
**结论：整段模式「切字头」的主因不是缺 speech_pad，而是 (a) `min_speech_duration` 被调小、(b) `threshold` 太高导致起音被判静音、(c) 流式模式那 0.4 s 预录被吃掉。**

**句尾不会丢**：`end = buffer_.Tail() - MinSilenceDurationSamples()`（同上 `:112`），
切点落在「最后一次非静音帧」附近，尾部静音被减掉、最后的音素被保留。
真正会丢句尾的是**流式模式**（`asr.rs:22` 的 `TAIL_SILENCE_SAMPLES = 4800` = 300 ms 补静音）和 `Recorder::stop()` 抢先取样。

#### 2.3 与 Silero 官方默认值的对照（本项目目前偏保守）

Silero 官方 Python `get_speech_timestamps()` 默认（[src/silero_vad/utils_vad.py](https://github.com/snakers4/silero-vad/blob/master/src/silero_vad/utils_vad.py) 第 281-296 行）：

```python
threshold: float = 0.5,
min_speech_duration_ms: int = 250,
max_speech_duration_s: float = float('inf'),
min_silence_duration_ms: int = 100,      # ← 官方 100 ms
speech_pad_ms: int = 30,
neg_threshold: float = None,             # ← 默认 threshold - 0.15
```

| 参数 | Silero 官方 | sherpa 默认 | **本项目现状**（`asr.rs:68-83` / `385-399`） |
|---|---|---|---|
| `threshold` | 0.5 | 0.5 | 0.5 ✅ |
| `min_speech_duration` | 0.25 s | 0.25 s | 0.25 s ✅ |
| `min_silence_duration` | **0.10 s** | **0.50 s** | **0.50 s** ⚠️ 偏保守 5 倍 |
| `max_speech_duration` | ∞（不限） | 20 s | 30 s（整段）/ 20 s（流式） |
| 句首留白 | 30 ms（`speech_pad_ms`） | ~314 ms（隐式） | ~314 ms（隐式） |

→ **本项目 `min_silence_duration = 0.5` 是「句子拖太长带静音」的最直接原因**：
任何 <500 ms 的停顿都被粘进同一段，SenseVoice 就拿到一段中间带空洞的长音频。

#### 2.4 可操作的调参建议

> 原则：**一次只改一个参数**，用 `cargo test --test quality_probe -- --nocapture` 量化。
> 该测试已内置 `norm()`（去标点空白）与 `edit_distance()`（逐字编辑距离），样本 `tests/fixtures/zh.wav`、`zh-tail.wav`、`zh-tail2.wav`
> 正好覆盖「整句 / 尾字 / 尾字」三类问题（见 `src-tauri/tests/quality_probe.rs`）。

| 症状 | 首选动作 | 备选 | 注意 |
|---|---|---|---|
| 切句太碎、每句很短 | **先做 §4 的短句合并**（改结构，收益最大）；其次 `min_silence_duration` 0.5→**0.3** | `min_speech_duration` 0.25→0.15 | 调小 `min_speech_duration` 会**缩短句首留白**，可能加剧切字头 |
| 句子拖太长、中间带静音 | `min_silence_duration` 0.5→**0.25~0.3** | — | 直接影响尾部保留的静音量，改完必须看「句尾是否被切」 |
| 切掉字头 | `min_speech_duration` 0.25→**0.3**（句首留白 314→414 ms） | `threshold` 0.5→0.45 | 别再用「加 speech_pad」的思路找原因（sherpa 没有这个参数） |
| 噪声里冒出假句子 | 先换 **Silero v5**；仍不行再 `threshold` 0.5→0.6 | 引入 GTCRN 降噪（§3） | 升 threshold 会同步抬升 `neg_threshold`，更容易切碎 |
| 句尾丢字（整段模式） | 检查 `Recorder::stop()` 顺序（已知坑）；确认 `min_silence_duration` 没被调得过大 | — | sherpa 的 `end = Tail - MinSilenceDurationSamples` 本身不丢尾音 |
| 句尾丢字（流式模式） | 确认 `TAIL_SILENCE_SAMPLES = 4800`（300 ms）仍在 | 试 400 ms | 这条与 VAD 参数无关 |

#### 2.5 `max_speech_duration` 的正确用法（附一个反直觉结论）

上游逻辑（`voice-activity-detector.cc:51-53`）：

```cpp
if (buffer_.Size() > max_utterance_length_) {
  model_->SetMinSilenceDuration(new_min_silence_duration_s_);  // 0.1
  model_->SetThreshold(new_threshold_);                        // 0.90
}
```

* `buffer_.Size()` ≈ 当前句长 + 约 0.32 s 尾巴，所以 `max_speech_duration` 是「**当前句长超过它就进入收紧态**」。
* 收紧后 min_silence 变成 **0.1 s**（比项目正常值 0.5 s 激进 5 倍）、threshold 变成 **0.9**（比 0.5 激进很多）。
  → **中文连续语流里 100 ms 的音节间隙非常常见**，收紧态下会被切得很碎。
* 而且这两个值**硬编码**，你无法用配置把它们调回温和。

**因此：把 `max_speech_duration` 调小 = 主动让系统更早进入「激进切分」状态**，收益（防止超长句）远小于代价（句子变碎）。
除非你实测到「经常出现 >30 s 的单句」，否则**建议保持 30 s 不动**。

真正该做的是**把 buffer 与 max_speech_duration 对齐**：

* 整段录音路径 `asr.rs:485`：`VoiceActivityDetector::create(&vad, 60.0)` ✅（60 s 缓冲 ≥ 2×30 s）
* **文件转写路径 `asr.rs:114`：`VoiceActivityDetector::create(vad_config, MAX_SEGMENT_SECONDS + 2.0)` = 32 s ⚠️**
  → 32 s 缓冲配 30 s 的 `max_speech_duration`，留给「收紧态还能继续长」的余量只有 2 s。
  一旦超过，CircularBuffer 会按 `circular-buffer.cc:109-123` **扩容并整段拷贝**（打 `Overflow!` 日志）。
  **建议统一成 60 s。**（这是本次调研发现的现存不一致，属低风险单行修复。）

#### 3.2 GTCRN：数据与可行性

官方仓库 [Xiaobin-Rong/gtcrn](https://github.com/Xiaobin-Rong/gtcrn)（ICASSP 2024, [论文](https://ieeexplore.ieee.org/document/10448310)）：

* **48.2 K 参数、33 MMAC/s**（比 RNNoise 的 0.04 GMAC/s 还略低）。
* 流式 RTF = **0.07**（12 代 Intel i5-12400 @2.5 GHz，仓库 README「Streaming Inference」节）。
* 质量（仓库 README Table 1 / Table 2）：

| | VCTK-DEMAND SI-SNR | VCTK-DEMAND PESQ | DNS3 OVRL |
|---|---|---|---|
| Noisy | 8.45 | 1.97 | 2.33 |
| RNNoise (2018) | – | 2.29 | 2.53 |
| DeepFilterNet (2022) | 16.63 | 2.81 | **–** |
| **GTCRN** | **18.83** | **2.87** | **2.70** |

→ **GTCRN 明显优于 RNNoise**，与算力更大的 DeepFilterNet 打平或更好。

sherpa-onnx 侧（[speech-enhancement 页](https://k2-fsa.github.io/sherpa/onnx/speech-enhancement/models.html)）：

* 模型 `gtcrn_simple.onnx` = **523 KB**（我实测 535 638 字节，sha256 `e77603ac0c23dac3227dd2d7135b3a585cbee2679048aecfa886657d3ae1b534`）。
* 官方给的 CPU 实测：2.4 s 音频耗时 0.171 s → **RTF 0.071**（macOS，Apple Silicon）。
* sherpa-onnx 从 [PR #1977](https://github.com/k2-fsa/sherpa-onnx/pull/1977)（2025-03-10）起支持 GTCRN。

**DPDFNet**（[sherpa 文档](https://k2-fsa.github.io/sherpa/onnx/speech-enhancement/dpdfnet.html)，[论文 arXiv:2512.16420](https://arxiv.org/abs/2512.16420)）：

* DeepFilterNet2 + Dual-Path RNN，8/16/48 kHz 都有官方 ONNX；16 kHz 变体 `dpdfnet_baseline`（2.31 M 参数 / 0.36 GMAC）到 `dpdfnet8`（3.54 M / 4.37 GMAC）。
* 有一个很实用的旋钮：**`attenuation_limit_db`（仅离线）**，把一份带噪频谱按 `10^(-L/20)` 混回去，抑制「过度抑制」。
  官方默认 0（关闭）。→ 降噪过头导致 ASR 掉字时，把它调到 6~12 dB。
* 模型在官方 HF 仓库 [`Ceva-IP/DPDFNet`](https://huggingface.co/Ceva-IP/DPDFNet)（commit `dd6818d00f50c836fed43a6243ebe49116de5964`，含 `onnx/*.onnx`）。

**三个必须提前知道的坑**

1. **下载可得性不理想**：`gtcrn_simple.onnx` **只在 GitHub Releases**
   （`https://github.com/k2-fsa/sherpa-onnx/releases/download/speech-enhancement-models/gtcrn_simple.onnx`），
   **k2-fsa / csukuangfj 的 HF 账号下没有官方镜像**（我查过 `k2-fsa` 与 `csukuangfj` 的全部 HF 仓库，没有 speech-enhancement / gtcrn / dpdfnet）。
   → 与本项目「hf-mirror 优先、失败再回退 HF」的下载编排不兼容；GitHub 在国内又不稳（项目已经为 `sherpa-onnx-sys` 踩过这个坑，
   用 `SHERPA_ONNX_ARCHIVE_DIR` 兜底）。
   → 若要做，建议加一个**可选资产 + 本地目录导入**，或用第三方 HF 镜像（`bitsydarel/gtcrn-onnx` 等，**非官方，需自行校验 sha**）。
2. **降噪会伤干净语音**：SE 模型在低 SNR 下过抑制、吃掉辅音，直接反映为 CER 上升。
   → **必须做成「可选开关、默认关」**，并且用同一批样本对比开关前后的 CER。
3. **顺序问题**：降噪应该在 **VAD 之前**（VAD 判的就是噪声抑制后的语音概率），还是在 **VAD 之后**（只对切出的句子降噪，浪费更少）？
   → 建议 **VAD 之前**（在线/流式尤其如此：VAD 门控决定喂不喂模型，噪声会让门控误开）；
   离线模式也可以先切句再降噪（省算力），但那样 VAD 仍会受噪声影响。**两种都要实测。**

#### 3.3 RNNoise / DeepFilterNet：需要新依赖，且都不如 GTCRN

| 方案 | Rust 侧 | 状态 | 结论 |
|---|---|---|---|
| **GTCRN** | sherpa-onnx 内建 | 官方维护，2025-03 起 | ✅ 首选 |
| **DPDFNet** | sherpa-onnx 内建 | 官方维护，2025-12 论文 | ✅ 备选（可 48 kHz，有 `attenuation_limit_db`） |
| **DeepFilterNet** | `deep_filter` crate | **0.2.5，最后更新 2022-07-28**（4 年未动）；1.8 M 参数 / 0.35 GMAC（比 GTCRN 重 10 倍） | ❌ 质量与 GTCRN 打平但更重、crate 更陈旧 |
| **RNNoise** | `rnnoise-sys` 0.1.2 / `rnnoise-c` 0.1.0（无 `rnnoise` 本体） | 质量被 GTCRN 明显超过（见上表） | ❌ |
| **WebRTC NS** | `webrtc-audio-processing` 2.1.0（2026-05-13） | **需要编 C++ WebRTC**（`bundled` feature 要 clang/gcc + pkg-config + meson + ninja） | ⚠️ 工具链负担重，见 §3.4 |
| **WebRTC NS/AGC（纯 Rust）** | `sonora` 0.2.0（2026-07-29） | 纯 Rust 移植 WebRTC M145→M156，**MSRV 1.91** | ⚠️ **本项目声明 `rust-version = "1.78"`（`src-tauri/Cargo.toml`）→ 直接破 MSRV** |

#### 3.4 AGC：目前项目里**完全没有**这一环

现状（`src-tauri/src/audio.rs:458-477`）：

```rust
for frame in data.chunks(channels) {
    let mut sum = 0f32;
    for sample in frame { sum += f32::from_sample(*sample); }
    self.mono.push(sum / frame.len() as f32);
}
```

* 只做了**多声道平均**（多声道取均值会在相位相反时互相抵消，是个潜在隐患，但一般麦克风不是反相的），**没有任何增益控制**。
* `LevelRing::peak()`（`audio.rs:109-117`）其实算的是 **RMS×6** 的电平，**不是真峰值**，所以**检测不到削波**。
* 后果：
  * **增益过低** → 语音概率上不去，VAD 判不出语音（整句丢失）；SenseVoice 也会输出空串。
  * **增益过高** → 削波（削顶的波形谐波失真极重），SenseVoice 准确率断崖式下降，而且**事后无法修复**（信息已丢失）。

**建议（三选一，从轻到重）**

1. **最轻（推荐）**：在应用内加一个 ~30 行的**峰值归一化 + 软限幅 + 慢速增益跟随**，
   并在 `audio:level` 事件里带一个 `clipped: bool`（真峰值 ≥ 0.99）让 UI 提示「麦克风增益过高」。
   零新依赖、零 MSRV 影响。
2. **中等**：`sonora` 的 AGC2（WebRTC AGC2 + RNN VAD + limiter），纯 Rust、16 kHz 单声道全链路 4.2 µs / 10 ms 帧
   （[sonora README 基准](https://github.com/dignifiedquire/sonora)，Apple M4 Max，Rust 比 C++ 慢 1.07×）。
   **前提：把 `rust-version` 从 1.78 提到 ≥1.91**，并接受一个「AI 辅助移植」的较新项目。
3. **最重**：`webrtc-audio-processing` 2.1.0（NS + AGC + AEC + VAD 全套），但要编 C++ WebRTC。

> **本项目的实际收益排序**：先做「削波检测 + 提示」（几乎零成本，直接避免最不可挽回的失败），
> 再考虑「静音检测」（电平长期低于阈值时提示用户调增益）。真正的 AGC 收益有限，因为用户通常直接调系统/设备增益。

> **实测更正（2026-10-28，最终版）**：上面「增益过低 → VAD 判不出语音」这条**成立**，
> 而且是线上「整段没转写」的真正根因。此前用**干净 fixture**（`gain_probe`：把孤立人声压到
> -56.5 dBFS 仍认出 99.2%）下的结论是**误导性的** —— fixture 没有环境声，掩盖了电平敏感性。
>
> 换成**真实录音**（`mic_probe` 抓的房间声，同一段音频人为衰减）实测：
>
> | 电平（峰值） | 不处理 | 经 `audio::Agc` |
> | --- | --- | --- |
> | 正常 0.637 | 724 字 | 722 字 |
> | -25 dB（0.036） | 465 字 | **723 字** |
> | -30 dB（0.020） | 94 字 | **718 字** |
> | -35 dB（0.011） | **0 字** | **717 字** |
>
> **机制**（`sherpa-onnx/csrc/silero-vad-model.cc` 的 `IsSpeech()`）：语音要触发，
> 概率得**连续**高于阈值满 `min_speech_duration`；概率一掉回阈值以下，攒的进度立刻清零。
> 低电平时概率恰好在阈值附近抖 → 永远攒不满 → `voice-activity-detector.cc` 的非语音分支
> 只 `buffer_.Pop(...)` → 那段音频**静默消失**（日志、转写、界面零痕迹）。
>
> ⇒ 「AGC / 削波提示」这条线的优先级要提到**第一位**：不是「防削波」，而是**它本身就是
> 低电平录音的解药**。已实现 `audio::Agc`（目标 RMS 0.02 / 增益上限 32× / 软限幅）——
> 电平够就一个样本不动，只救偏小的。

#### 3.5 去混响

* sherpa-onnx **没有通用去混响模型**（没有 dereverberation）。
* 唯一与混响相关的是**说话人分离**里的 `sherpa-onnx-reverb-diarization-v1`（[docs](https://k2-fsa.github.io/sherpa/onnx/speaker-diarization/models.html)），
  它是「带混响的说话人分离」，不是通用去混响。
* GTCRN / DPDFNet 在训练分布内对轻度混响有一定鲁棒性，但不等于去混响。
* 结论：**桌面麦克风场景（近讲、桌面距离）混响不是主要误差源**；把它排在噪声之后。

### 4. 采集侧改进

#### 4.1 采样率：现状是对的，不要改

* SenseVoice 是 **16 kHz** 模型（官方 `model.py` 固定 16 kHz 输入；sherpa 侧 `OfflineSenseVoiceModelConfig` 也按 16 kHz 提取特征）。
* 项目用 `cpal` 的 `device.default_input_config()`（`audio.rs:335-341`）拿设备默认格式（macOS 一般 48 kHz F32），
  再用 `sherpa_onnx::LinearResampler::create(rate, 16_000)`（`lib.rs:458-462`）重采样。
* 这个 resampler **不是朴素线性插值**，是 Kaldi 的 **sinc 插值 + 抗混叠低通**
  （`sherpa-onnx/csrc/resample.cc`，cutoff = `0.99 × 0.5 × min(in,out)`，窗长 `num_zeros = 6`；
  见 `sherpa-onnx-1.13.8/src/resampler.rs:19-21`）。48 k→16 k 时截止频率 7 920 Hz，够用。
* sherpa 识别器**本身也会重采样**（`sherpa-onnx/csrc/offline-stream.cc:148-165`：采样率不等就用同一套 `LinearResample` 重采样到 16 k）。
  → 项目自己先降到 16 k 是**必需**的，因为 **VAD 强制要求 16 k**（`silero-vad-model.cc`：`Expected sample rate 16000` 否则 `exit(-1)`）。
* **结论：保持「48 k 采集 + 应用内 sinc 重采样到 16 k」**。
  反过来让 OS 直接给 16 k 反而更差：会丢掉可控的高质量重采样、且依赖系统各家的重采样实现。

#### 4.2 声道选择

* 现状是**多声道取算术平均**（`audio.rs:465-474`）。若某设备同时提供「麦克风」和「回放/线路」双通道，取平均会**把回放混进语音**。
* 建议：先探测 `supported.channels()`，若 >1，优先用 cpal 的**设备默认输入**（多数是单声道）；
  若是双通道麦克风阵列，取**能量最大的通道**通常比平均更好。
* 这一项**收益不确定但风险明确**，建议在设置页暴露「声道：自动 / 平均 / 仅左 / 仅右」。

#### 4.3 首尾静音裁剪

* 整段模式：**不需要**。sherpa 的 VAD 已经把首尾静音去掉（句首留白 ~314 ms、句尾静音被 `end = Tail - MinSilenceDurationSamples` 减掉）。
  句首那 314 ms 的留白反而是**有用的上下文**（保住爆破音/字头）。
* 流式模式：**需要**，而且已经有：
  * 起音前 0.4 s 预录（`lib.rs:563`：`preroll_limit = 16000/5*2 = 6400` 样本 = 0.4 s），
  * 句尾 300 ms 补静音（`asr.rs:22` `TAIL_SILENCE_SAMPLES = 4800`）。
  → 这两处是流式模式「不切字头/不丢句尾」的关键，改动前务必用 `zh-tail.wav` / `zh-tail2.wav` 两个 fixture 回归。

#### 4.4 `speech_pad` / 预录缓冲对「切掉字头」的影响（汇总）

| 模式 | 句首留白来源 | 现状 | 是否够 |
|---|---|---|---|
| 整段（离线录音） | sherpa 隐式：`2×WindowSize + min_speech_duration` | ≈ 314 ms | **够**；再调 `min_speech_duration` 反而是主要旋钮 |
| 整段（文件转写） | 同上 | ≈ 314 ms | 同上 |
| 流式 | 显式预录缓冲 0.4 s | 400 ms | **够**；注意 `preroll` 只在 `active` 由 false→true 时一次性灌入（`lib.rs:623-625`），别改这个语义 |

  ```python
  vad_model="fsmn-vad",
  vad_kwargs={"max_single_segment_time": 30000},
  merge_vad=True,        # ← 把短碎片合并
  merge_length_s=15,     # ← 合并到 15 秒
  ```
* 无 VAD 的长音频兜底脚本 `long_audio_no_vad.py`：
  * 固定 **30 s 窗 + 2 s 重叠**；
  * 「The merged transcript removes only **exact** text repeated across adjacent window boundaries」；
  * 「**fixed boundaries can still change recognition around a cut**」；
  * 「The VAD pipeline above remains the **recommended default** when content-based segmentation is acceptable.」

#### 5.2 与本项目的对照

| 项 | 官方 | 本项目 | 评价 |
|---|---|---|---|
| 单次送入长度 | ≤30 s（建议） | 整句一次，≤90 s（`asr.rs:184` `MAX_SINGLE_SHOT_SECONDS = 90`） | 官方是**建议**不是硬约束；项目实测 55 s/130 s 都是 98.6%，且切了反而 97.9%（AGENTS.md 已记录）→ **保持现状** |
| 超过 90 s 的兜底 | 30 s 窗 + 2 s 重叠 | 同（`asr.rs:190-191` `WINDOW_SECONDS=30 / OVERLAP_SECONDS=2`） | ✅ 一致 |
| 合并算法 | `merge_transcripts(texts, min_overlap_chars=4, max_overlap_chars=200)`，**只删精确重复** | `asr.rs:193-195` 同样用 4 / 200，但 `overlap_cut()` **忽略标点**比较（`is_merge_punct`） | ⚠️ 项目比官方**激进**：官方只删精确重复，项目会跨标点对齐后删除，可能删掉真实文本。建议改成「先精确匹配，匹配不上再退化到忽略标点」 |
| 分段边界 | VAD 内容边界（FSMN-VAD） | sherpa Silero VAD | ✅ 方向一致 |
| 短碎片合并 | `merge_vad=True, merge_length_s=15` | **无** | ❌ **缺失，是最大的结构性差距**（见 §5.4） |

#### 5.3 更好的切分/合并方式（按推荐度）

1. **【最优】按 VAD 边界切 + 合并短碎片**（而不是固定窗）。
   本项目已经有 VAD 边界，只需要加一层「合并缓冲」：
   * 维护一个待发句缓冲；新句到来时，若「缓冲 + 新句 ≤ 目标长度（如 15~20 s）」就合并，否则先发出缓冲再开新缓冲。
   * 对齐 FunASR 的 `merge_vad=True, merge_length_s=15`。
   * 收益：每句更长 → SenseVoice 上下文更足 → CER 更低；同时句子数减少 → 推理次数减少 → 更省电。
   * 代价：`stream:segment` 事件的粒度变粗（前端要接受「一句可能 15 s」）。
   * 侵入性：中（`asr.rs` 加一个合并器；前端 `result.js` 的分段展示可能要跟着调）。
2. **【次优】超长句（>90 s）不要用固定 30 s 窗，改成在句内再跑一次 VAD 找静音点切**。
   现状的 30 s + 2 s 是官方兜底方案，官方自己都说「fixed boundaries can still change recognition around a cut」。
   由于 >90 s 的单句极少见，**优先级低**，但可以把 `recognize_segment()` 里的固定窗换成「对这段再跑一遍 VAD」。
3. **【不建议】调大 `MAX_SINGLE_SHOT_SECONDS`**。编码器注意力随帧数平方增长，显存/内存不划算；官方 30 s 建议也没说要放宽。
   保持 90 s。

#### 5.4 中文长句上的已知差异（SenseVoice vs 拼接 vs 流式）

* SenseVoice 是**非自回归整段模型**：一次性吃整句，句内上下文完整 → 同一段音频整喂比切窗喂更准（项目实测 98.6% vs 97.9%）。
* 反过来，**跨句上下文丢失**：SenseVoice 无状态，每句独立识别；「明天 / 今天」这类词它没有前后句可依
  （AGENTS.md 已记录：SenseVoice 会把「明天」听成「今天」）。
  → 这正是**§5.3 第 1 条（合并短句）**的价值：合并让每句更长，句内上下文更多。
* 流式 Zipformer transducer 是**因果**的，只能看左上下文 → 长中文连读时更易错（项目实测流式 99% vs SenseVoice 91%，见 AGENTS.md）。
* 结论：**整段模式 + 更长的合并句 = 中文长句的最佳解**。

### 6. 说话人切换（说话人分离）

* sherpa-onnx 1.13.8 **有** `OfflineSpeakerDiarization`
  （`sherpa-onnx-1.13.8/src/offline_speaker_diarization.rs:102-121`）：
  `segmentation: OfflineSpeakerSegmentationModelConfig`（pyannote，`window_shift_ratio`）
  + `embedding: SpeakerEmbeddingExtractorConfig`（3D-Speaker / NeMo）
  + `clustering: FastClusteringConfig`（`num_clusters`、`threshold`、`compute_confidence`）
  + `min_duration_on: 0.3` / `min_duration_off: 0.5`。
* 模型在 GitHub Releases（[speaker-segmentation-models](https://github.com/k2-fsa/sherpa-onnx/releases/tag/speaker-segmentation-models)、
  [speaker-recongition-models](https://github.com/k2-fsa/sherpa-onnx/releases/tag/speaker-recongition-models)），
  同样**没有官方 HF 镜像** → 与项目下载策略冲突。
* **架构冲突**：diarization 是**离线 API**（`process(&self, samples: &[f32])`，需要整条音频），
  与本项目「边录边识别、内存恒定、无限录音时长」的承诺直接冲突。
* 官方 FunASR 的等价组合是 `fsmn-vad` + `cam++` + `ct-punc`（[SenseVoice README](https://github.com/FunAudioLLM/SenseVoice)）。
* **结论**：除非产品明确要「说话人 1 / 说话人 2」标签，否则**不做**。
  若真要做，注意它是「离线标注」能力，不是「分段质量」能力——它对切句质量的提升远小于 VAD 本身。

| 1 | **换 FSMN-VAD** | sherpa-onnx 1.13.8 的 `VadModelConfig` 根本没有这个字段（`src/vad.rs:64-71`；C API 同）。要用只能装 FunASR(Python) 或换 llama.cpp → 等于换掉整个栈。 |

| 3 | **换 TEN-VAD** | 质量（Multi-Domain ROC-AUC 0.93）低于 v5（0.96）、纯噪声准确率 0.42 低于 v4 的 0.51；且官方承认 pitch 特征被置 0「may degrade the performance」；只在 GitHub Releases，没有 HF 镜像。 |
| 4 | **把 `max_speech_duration` 大幅调小（如 10 s）** | 触发的收紧参数 **0.1 s / 0.9 是上游硬编码**（`voice-activity-detector.cc:228-229`），改不了；中文连续语流里 100 ms 音节间隙极常见 → 会切得很碎，收益（防超长句）远小于代价。 |
| 5 | **在整段模式上再套一遍标点模型** | SenseVoice 开 ITN 时自己就输出标点，会叠成「。。」。AGENTS.md 已记录，不要再加回来。 |
| 6 | **用 SenseVoice 覆盖流式结果** | 项目实测流式 99% vs SenseVoice 91%；且与「复核要保留全部音频、内存恒定」的承诺冲突。AGENTS.md 已记录。 |
| 7 | **让 OS 直接给 16 kHz** | 会丢掉应用内 Kaldi sinc 抗混叠重采样（`resample.cc`），质量依赖系统实现。保持 48 k 采集 + 应用内重采样。 |
| 8 | **引 `webrtc-audio-processing`（C++ WebRTC APM）** | 需要 `bundled` feature 编译 WebRTC C++（clang/gcc + pkg-config + meson + ninja），把一个 Rust/Tauri 桌面应用的构建链搞重；且 NS+AGC 与 GTCRN/自研 AGC 收益重叠。 |
| 9 | **引 `sonora`（纯 Rust WebRTC APM）** | **MSRV 1.91**，直接破本项目声明的 `rust-version = "1.78"`（`src-tauri/Cargo.toml`）；且是 2026 年的新项目（README 标注 AI 辅助移植）。 |
| 10 | **用 DeepFilterNet / RNNoise 替代 GTCRN** | `deep_filter` crate 最后更新 2022-07-28（4 年陈旧）；DeepFilterNet 1.8 M 参数 / 0.35 GMAC（GTCRN 48 K / 33 MMAC）；质量上 GTCRN 已持平或更好（PESQ 2.87 vs 2.81、DNS3 OVRL 2.70 vs RNNoise 2.53）。 |
| 11 | **默认开启降噪** | SE 模型在低 SNR 下会过抑制、吃掉辅音，直接推高 CER；且 GTCRN 只有 GitHub Releases 可下（无官方 HF 镜像）。→ 做成**可选开关、默认关**，用 CER 决定是否开。 |
| 12 | **引说话人分离模型** | 仅离线 API，与「边录边识别、内存恒定」冲突；模型只有 GitHub Releases；对「切句质量」的提升远小于 VAD 本身。 |
| 13 | **把 `merge_transcripts` 的「忽略标点匹配」改成更激进** | 官方 `long_audio_no_vad.py` 明确只删**精确重复**；跨标点对齐后删除可能删掉真实文本（宁可重复也别丢话）。若要改，应该是「先精确、失败再退化」，而不是相反。 |
| 14 | **在没有量化 CER 之前改 VAD 参数** | 本项目已有现成的量化入口（`src-tauri/tests/quality_probe.rs` 的 `norm()` + `edit_distance()`，样本 `zh.wav` / `zh-tail.wav` / `zh-tail2.wav`）。没有量化就调参＝玄学。 |
