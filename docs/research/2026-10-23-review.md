## 二、必须修正的三处

### 1. 撤销「`auto` 语言会打错误日志」（路线图 P0-4 作废）

v1.13.8 的 SenseVoice 元数据里语言表是：

```cpp
std::unordered_map<std::string, int32_t> lang2id{
    {"auto", 0}, {"zh", 3}, {"en", 4}, {"yue", 7}, {"ja", 11}, {"ko", 12},
};
```

`"auto"` 是**一等公民**，不会进 `Unknown language` 分支。本机分别用 `"auto"` / `"zh"` 建引擎并转写 3 条样本，
输出逐字相同、stderr 无报错。**现有代码传 `settings.language`（默认 `"auto"`）是正确的，不需要改。**

> 这条错误的来源：调研 agent 对照的是 master 分支源码；master 与 v1.13.8 在这段虽同构，但 master 的
> `lang2id` 是否含 `"auto"` 未逐字核对，属于「拿别处源码推断本项目版本行为」。

### 2. 收回「热词漏设 `modeling_unit` 会杀进程」

`c-api.cc:142`：

```cpp
SHERPA_ONNX_OR(config->model_config.modeling_unit, "cjkchar");
```

C API 在 Rust 传 `None` 时**自动补成 `"cjkchar"`**，所以本项目这种 char-based 流式模型**不设也能用热词**。
本机实验：`modeling_unit=None` 与 `Some("cjkchar")` 输出完全一致，且都成功把「在」纠成「再」。

真正需要显式设置的是**换 X-ASR（bpe 模型）时** —— 那时默认的 `cjkchar` 是错的，必须设 `"bpe"` + `bpe_vocab`。

### 3. 标点 int8 的三点收窄（P0-1 从「3 个常量」降级为「需先解决托管」）

- **体积**：75,519,198 B（72 MiB），相比 fp32 294,372,519 B **省 209 MiB** —— 数字成立。
- **质量**：7 句对比，6 句逐字相同；唯一差异是 int8 把「这个功能的验收标准**，**我们再确认一下。」
  的句中逗号丢了。**不是「完全不变」，是「有轻微损失」**。
- **速度**：本机 7 句 26 ms（int8）vs 17 ms（fp32）—— 与「int8 更快」的说法相反（单次测量，可能受首次加载影响，
  但至少不能把「更快」当卖点）。
- **托管**：官方 HF 仓库 `csukuangfj/sherpa-onnx-punct-ct-transformer-zh-en-vocab272727-2024-04-12`
  只有 `model.onnx`（fp32）；int8 只出现在 GitHub Releases 的 `-int8.tar.bz2` 与第三方 HF 再上传
  （`ranger810/`、`lorneluo/`、`ifreeking/`）。本项目下载器是「HF 镜像优先」，**直接换成 int8 会 404**，
  需要先决定：GitHub release 直链（国内可达性问题）/ 固定第三方镜像 sha / 自己量化托管。

## 三、无法在本地验证（如实列出）

| 结论 | 为什么验不了 | 影响 |
|---|---|---|
| VAD v4→v5 在噪声/会议上的收益（ROC-AUC 0.83→0.94） | 只有 3 条干净短句，v4/v5 切句完全一致 | 仍是「上游数据支持」，不是「我们测过」 |
| 热词 48/140→94/140、6/30→22/30 | 第三方单机基准，需要同样的 140 句合成集 + 30 句真实录音 | 只能作为方向证据 |
| FireRed ASR2 / Qwen3-ASR 的中文 CER | 需要下载 800 MB 级模型并跑同一套语料 | 换模型决策仍缺本地数据 |
| Qwen3-ASR `max_total_len` 截断长音频 | 未下载模型 | P2-1 的坑未实测 |
| LLM 后编辑的逐句延迟（0.5–2 s） | 未装 llama.cpp / 未下 GGUF | 结论来自官方基准，属合理推断 |
| Windows 上热词的 CPU 表现 | 本机是 macOS arm64 | 热词延迟需 Windows 侧复测 |

## 四、复核结论

1. **路线图骨架成立**：P1 的三件事（流式热词、rule3、同音词替换）仍然是性价比最高的方向，
   且其中两件已被本机实验直接证实（热词纠错、20 s 硬切）。
2. **P0 需要调整**：撤销 P0-4（`auto` 语言）；P0-1（标点 int8）从「3 个常量」改为「需先解决托管 + 接受轻微质量损失」；
   P0-2（VAD v5）、P0-3（32s→60s）、P0-5（探针）不受影响。
3. **两份调研里的「致命细节」要区别对待**：真正会让应用闪退的是「离线 SenseVoice + beam/热词」，
   这一条已本机复现；而「漏设 modeling_unit 会闪退」是误报，已收回。
4. **最大的缺口没变**：没有真实语料，所有「提升多少」都停留在上游数字。复核不改变这个结论。
