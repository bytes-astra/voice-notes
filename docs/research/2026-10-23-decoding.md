## 1. 结论摘要

| 手段 | 预期收益 | 代价 | 对本项目的侵入性 | 可行性 |
|---|---|---|---|---|
| **流式模式开热词**（`hotwords_file`/`hotwords_score` + `decoding_method="modified_beam_search"` + `modeling_unit="cjkchar"`） | 专名/术语命中率实测 **48/140 → 94/140**（int8，boost 3）；真实录音 **6/30 → 22/30**。RTF 基本不变（0.031→0.029，编码器占大头） | 解码变慢（beam 相对 greedy，66 分钟长录音上 0.031→0.029 反而更快，但短音频上解码器是瓶颈）；**可能把词硬塞进没说的句子里**（实测 140 句里 2 句、30 句里 2 句） | 中：`StreamingEngine::new` 加 3 行 + 一个热词文件 + 前端一个「术语表」入口 | ✅ **高**（transducer 原生支持） |
| **离线模式拼音同音词替换**（`hr.lexicon` + `hr.rule_fsts`） | 官方示例（**正是本项目的 SenseVoice 模型**）：`悬界芯片/工投安装/基载传感器` → `玄戒芯片/弓头安装/机载传感器` | 需要 `lexicon.txt`（官方发布）+ 自建 `replace.fst`（要 pynini 在 Linux 上生成）；规则文件目前**不支持动态修改** | 中：`Engine::new` 加 `config.hr`，加 2 个 assets 下载 | ✅ **高**（对 SenseVoice 生效，任何解码方法都生效） |
| **离线模式热词** | ❌ **无效** | — | — | ❌ **不可行**（SenseVoice 无 context graph） |
| **`decoding_method="modified_beam_search"`（不加热词）** | 小幅：Vosk 0.52 CER 3.64%→3.50%、WER 14.53%→14.25%；Parakeet int8 FLEURS 英 8.50%→9.04%（**变差**） | 解码 1.7–11× 慢（取决于长短音频） | 低（改 1 行） | ⚠️ **中**（收益不稳定，可能负收益） |
| **`blank_penalty` 微调**（transducer 专用） | 抑制「吃字」：正值抬高非 blank 概率 → 删除减少、插入增加。适合模型爱吞字的环境 | 调过头会插入重复字 | 低（改 1 行） | ✅ **高**（可先只对流式开） |
| **端点规则调参**（`rule3_min_utterance_length` 等） | 修掉「连续说话每 20 秒被硬切一刀」的隐藏问题 | 无 | 极低 | ✅ **高** |
| **VAD 参数重调**（`threshold`/`min_silence_duration`/`min_speech_duration`/`max_speech_duration`） | 切句质量直接决定 SenseVoice 逐句准确率；切碎=上下文丢、切长=句子过长 | 需要重跑回归样本 | 低 | ✅ **高**（但必须实测） |
| **外挂 WeTextProcessing ITN（`rule_fsts`）** | 流式模式目前**完全没有 ITN**（zipformer 不输出 ITN 文本），这是唯一补法；离线模式**已有** SenseVoice 内置 ITN | 需要生成 FST 资源（几十 MB）；与 SenseVoice 内置 ITN **叠加会二次规整**，把「2025年」改成「2025年」通常没事，但「15-6」这类会被改坏 | 中 | ⚠️ **中**（只建议给流式用） |
| **两遍 / 融合（ASR+LLM 纠错、ROVER、字典重打分）** | LLM 纠错对专名有效（akou：Parakeet fp32+热词 27/30 vs Qwen3-ASR 1.7B 28/30，差距不大） | 需再塞一个 LLM 运行时（llama.cpp），**内存 ×3、RTF 3–13× 慢**；且**与本项目「消费式缓冲、内存恒定、边录边出字」直接冲突**（LLM 需要完整句子） | 高 | ❌ **低**（不推荐） |
| **外接 n-gram LM（`lm_config`）做 decoder 端重打分** | 只对 transducer 有用；SenseVoice 直接忽略 | 加载 arpa/kenlm 慢、占内存；对 3M 中文小模型收益远小于热词 | 中 | ❌ **低** |
| **加 Qwen3-ASR / FunASR-Nano（sherpa-onnx 1.13.8 已支持）** | 名字识别更强 | 这是换模型；内存 ×3、RTF 3–13× 慢；下载 2.5 GB | 高 | ❌ **超出本题范围** |

**一句话建议（按性价比排序）**：
1. **流式模式接热词**（唯一一个 sherpa-onnx 原生、被官方文档明确支持、对专名有 2–3 倍提升、且 RTF 几乎不变的手段）；
2. **离线模式接拼音同音词替换**（因为 SenseVoice 不支持热词，这是离线模式唯一能修「专名/术语同音错字」的原生手段）；
3. **调 `rule3_min_utterance_length`**（修掉连续说话被 20 秒硬切）；
4. 其余（beam search、blank_penalty、VAD 调参）属于「先测再上」，不要盲改。

## 2. 逐项详述

### 2.1 上下文偏置 / 热词（hotwords / contextual biasing）

#### 是什么

把待识别的专名/术语/产品名编译成 token 序列，在解码时用 **Aho-Corasick 自动机**在 token 级给部分匹配的路径加权；匹配失败时把加的分数**退掉**（所以不会误伤）。加的分数按 token 在短语上**均摊**。

一手来源：
* 官方文档（sherpa）：<https://k2-fsa.github.io/sherpa/onnx/hotwords/index.html> —— 明确写「**Only transducer models support hotwords**」「必须改用 `modified_beam_search`，默认的 `greedy_search` 不支持热词」「四个额外参数：`hotwords-file` / `hotwords-score` / `modeling-unit` / `bpe-vocab`」。
* 实现：`sherpa-onnx/csrc/context-graph.h`（Aho-Corasick + 退分）、`csrc/utils.cc:104-205`（`EncodeHotwords`，文件格式解析）、`csrc/offline-recognizer-transducer-impl.h:109-120,262-280`（离线）、`csrc/online-recognizer-transducer-impl.h:116-119,443-499`（流式）。
* Rust 侧字段：`src/offline_asr.rs:563-564`（`hotwords_file` / `hotwords_score`）、`:679-683`（`create_stream_with_hotwords`）；`src/online_asr.rs:272-273,282`（同上）、`:382-386`（`create_stream_with_hotwords`）。

#### 文件格式与 score 语义

* **每行一个热词**，词之间用空格分隔（`语音识别` / `DEEP LEARNING`）。
* **可选的 per-hotword 加权分数必须写在行尾**，形式 ` 语音识别 :3.5`（冒号前的空格可有可无，分数是最后一个 token）。写成 `SPEECH :2.0 识别` 会被判为非法并 `return false`（`csrc/utils.cc:119-135`）。
* `hotwords_score` 是**全局默认分**，作用在 **token 级**（官方文档原文：「The boosting score for each matched token」），默认 **1.5**。
* 匹配到热词时按 token 均摊：`per_token_boost = hotwords_score / 词内 token 数`（issue #2937 的官方回复，2025-12-25）。

#### 在本项目怎么接

**流式模式（可做）：** 本项目流式模型是 `csukuangfj/sherpa-onnx-streaming-zipformer-zh-int8-2025-06-30`，来自 `yuekai/icefall-asr-multi-zh-hans-zipformer-large`，icefall 官方页面写明是 **char-based（cjkchar）** 训练（<https://github.com/k2-fsa/icefall/blob/master/egs/multi_zh-hans/ASR/RESULTS.md>），所以：

```rust
// src-tauri/src/asr.rs :: StreamingEngine::new()
let mut config = OnlineRecognizerConfig::default();
config.model_config.transducer = OnlineTransducerModelConfig { /* 现状不变 */ };
config.model_config.tokens = Some(paths.tokens.clone());
config.model_config.num_threads = threads();
config.model_config.provider = Some("cpu".into());

// ── 热词三件套 ───────────────────────────────
config.decoding_method = Some("modified_beam_search".into()); // 热词必须
config.max_active_paths = 4;                                  // 上游默认
config.model_config.modeling_unit = Some("cjkchar".into());   // 必须！否则进程被 _Exit
if let Some(hw) = &paths.hotwords {                           // 热词文件
    config.hotwords_file = Some(hw.clone());
}
config.hotwords_score = 2.0;                                  // 官方文档示例值
```

三个**必须同时满足**的前置条件（缺一不可，否则不是「不生效」而是「进程被杀掉」）：

1. `decoding_method == "modified_beam_search"`：上游 `csrc/offline-recognizer.cc:84-90` 校验「有 hotwords_file 但 decoding_method 不是 modified_beam_search」→ `Validate()` 返回 false → recognizer 创建失败（Rust 侧 `OfflineRecognizer::create` 返回 `None` → 本项目会弹「无法加载模型」）。**注意：这只是流式；离线 SenseVoice 见下。**
2. `modeling_unit` 必须是 `cjkchar` / `bpe` / `bbpe` / `cjkchar+bpe` 之一：`csrc/utils.cc:172-180` 的 else 分支是 `SHERPA_ONNX_LOGE(...) + SHERPA_ONNX_EXIT(-1)`，而 `SHERPA_ONNX_EXIT` 是 `_Exit(code)`（`csrc/macros.h:54-59`）—— **不展开栈、不跑析构、不弹错误框，直接把 Tauri 进程干掉**。本项目流式模型是 cjkchar，且**不需要** `bpe_vocab`。
3. `hotwords_file` 必须存在（`csrc/offline-recognizer.cc:99-104` 校验 `FileExists`）。

> **复核注记（2026-10-23）**：`modeling_unit` **不设也能用** —— C API `c-api.cc:142` 用 `SHERPA_ONNX_OR(..., "cjkchar")` 自动兜底；本机实测不设与设 `"cjkchar"` 输出完全一致。只有换 bpe 模型（如 X-ASR）时才必须显式设 `"bpe"` + `bpe_vocab`。

**每流热词 vs 全局文件：**
* 全局：`config.hotwords_file`（进程内所有流共享一份 Aho-Corasick）。
* 每流：`recognizer.create_stream_with_hotwords("语音识别/产品评审")`——斜杠分隔多个热词，**空格分隔同一个热词内的词**（上游注释：`"▁I ▁LOVE ▁YOU/▁HE LL O ▁WORLD"`）。每流热词与全局热词**会合并**（`csrc/online-recognizer-transducer-impl.h:221-242`）。项目里可以用每流热词做「本次录音的临时术语表」，用全局文件做「产品内置术语表」。

**离线模式（不可做）：** 本项目整段模式是 `sherpa-onnx-sense-voice-zh-en-ja-ko-yue-2024-07-17`，走 `csrc/offline-recognizer-sense-voice-impl.h`：
* 该 impl 的 `CreateStream()` 直接 `std::make_unique<OfflineStream>(config_.feat_config)`，**不带 context graph**（`:109-111`）；
* 该 impl 只认 `greedy_search`，给别的值直接 `SHERPA_ONNX_EXIT(-1)`（`:77-84`）——**给离线引擎设 `decoding_method="modified_beam_search"` 会直接杀进程**；
* **更狠的是 `create_stream_with_hotwords()`**：SenseVoice impl 没有重写带参数的 `CreateStream(hotwords)`，于是落到基类默认实现 `csrc/offline-recognizer-impl.h:36-40` → 打印「Only transducer models support contextual biasing.」后 `SHERPA_ONNX_EXIT(-1)` → **同样直接杀进程**（Rust 侧 `OfflineRecognizer::create_stream_with_hotwords` 正是调这条路径）；
* 官方文档：「All other models don't support hotwords」。

→ 离线模式想要「专名纠错」，请走 §2.2 的拼音同音词替换。**在 SenseVoice 上，热词不是「不生效」，而是「会把进程杀掉」。**

#### 预期收益（量化）

* 官方文档 cjkchar 示例：4 个中文人名全部由错转对（`文森特卡所→文森特卡索`、`蒋友伯→蒋有伯`、`周望军→周望君`、`朱立南→朱丽楠`），RTF 0.093→0.089（**没有变慢**）；cjkchar+bpe 流式示例：`LIBR→礼拜二`、`平凡的→频繁的`。
* 独立第三方基准（akou，2026，Apple M4 + sherpa-onnx-node 1.13.8，Parakeet TDT 0.6B v3）：<https://github.com/GeiserX/akou/blob/main/docs/research/asr-benchmark.md>

  | 配置 | 合成人名命中 /140 | 未出现的词被塞进去 /140 | 自己录音人名命中 /30 |
  |---|---|---|---|
  | int8 greedy 无词表 | 48 | 0 | 6 |
  | fp32 greedy 无词表 | 56 | 0 | 9 |
  | int8 beam + 词表（boost 3） | **94** | 2 | **22** |
  | fp32 beam + 词表（boost 3） | **96** | 1 | **27** |

  → 词表把人名命中率提升 **2–3 倍**；代价是「 hallucination 式误插」约 1.4–2%。**这正好是这个项目的核心场景**（会议/评审记录里的产品名、人名）。

#### 代价 / 风险

* **误触发**：热词 boost 会把「没说的话」拉成热词。官方文档与 akou 都提到；建议词表控制在几十条量级、boost 1.5–2.0 起步（官方示例 2.0；akou 用 3.0 只在极端场景）。
* **boost 越大越容易误插**；`hotwords_score` 是 token 级分数，cjkchar 模型下 4 个字的词每个字加 0.5（score 2.0）。
* **token 级概率不可信**：issue #2937（2025-12-25，官方回复）说明热词是解码期外部加分，不是模型概率，所以开了热词后 `ys_log_probs` 不再代表模型置信度。本项目目前不用置信度，无影响。
* **CPU**：beam search 比 greedy 慢。arXiv:2211.00484 表 5（V100）：greedy RTF 0.011 vs beam search 0.03（批处理）/0.126（非批处理）；onlybits 的 Vosk 对比：RTFx 48.2 → 29.0（**1.66× 慢**）。akou 在 66 分钟长录音上 0.031→0.029（编码器占大头，差异被摊薄）。→ **本项目流式是 200 ms 一片的实时链路，beam 的解码延迟要实测**（建议先只在「整段」以外的流式模式开，并测首字延迟）。

### 2.2 拼音词组匹配替换（Homophone Replacer）——离线模式唯一能修专名的原生手段

#### 是什么

对识别结果做**拼音级**的词组匹配替换：把识别出的汉字转成带声调的拼音，按用户写的规则（如 `xuan2 jie4 xin1 pian4` → `玄戒芯片`）替换。**只处理汉字**，非中文字符原样保留。

一手来源：
* 官方文档（中文页，sherpa）：<https://k2-fsa.github.io/sherpa/onnx/homophone-replacer/index.html>
* 实现：`sherpa-onnx/csrc/homophone-replacer.h`（`HomophoneReplacerConfig { dict_dir /* 1.12.15 起不再需要 */, lexicon, rule_fsts, debug }`）、`csrc/homophone-replacer.cc`、`csrc/phrase-matcher.h`。
* Rust 字段：`src/offline_asr.rs:568` 与 `src/online_asr.rs:284` 的 `hr: online_asr::HomophoneReplacerConfig`；`src/online_asr.rs:238-251`：`HomophoneReplacerConfig { lexicon: Option<String>, rule_fsts: Option<String> }`（`dict_dir` 被绑成 `ptr::null()`，注释「not used any more internally」）。
* 调用点：`csrc/offline-recognizer-impl.cc:912-933`（`ApplyInverseTextNormalization` / `ApplyHomophoneReplacer`）、`csrc/offline-recognizer-sense-voice-impl.h:246-247,292-293,367-368`（**SenseVoice 也走这两步**）、`csrc/online-recognizer-transducer-impl.h:370-371`（流式也走）。

官方文档原话：「支持 sherpa-onnx 里**所有能输出中文的语音识别模型**。不管是流式还是非流式，**不管采用何种解码方法**，都支持。例如，非流式的 SenseVoice，流式的 Zipformer 等等。」并且明确「本文所述的方法，与 `hotwords`（热词）是不同的技术，它们互相独立、毫不相关」。

#### 官方实测（用的就是本项目的模型）

SenseVoice + `sherpa-onnx-sense-voice-zh-en-ja-ko-yue-2024-07-17` 识别同一段音频：

| | 识别结果 |
|---|---|
| 不用该方法 | 悬界芯片 湖南人 工投安装 基载传感器 |
| 用该方法 | **玄戒芯片** 湖南人 **弓头安装** **机载传感器** |

（官方文档「结果比较」表 + `--debug=1` 输出 `homophone-replacer.cc:Apply:157` 等日志）

#### 在本项目怎么接

流式模式同理，改 `OnlineRecognizerConfig.hr`。**两种模式都能用**，这是它相对热词的最大优势。

资源：`lexicon.txt` 与示例 `hr-xuan-jie-replace.fst` 在官方发布页 <https://github.com/k2-fsa/sherpa-onnx/releases/tag/hr-files>。

#### 预期收益 / 代价 / 风险

* 收益：**专名/术语的同音错字**（玄戒/玄界、工投/弓头、基载/机载、悬界/玄戒）——这正是中文 ASR 最常见的错误类型之一。
* 代价：① 要写拼音规则（带声调数字）；② `replace.fst` 需要 **pynini** 生成，官方只有 Linux colab / 本地 Linux 一条路（Windows/macOS 不好装）——**这是本项目最大的落地障碍**；③ 规则文件目前**不支持动态修改**（官方原文：「规则文件，需要提前生成好。目前不支持动态修改规则文件」）；④ `lexicon.txt` 体积需实测。
* 风险：**误替换**。规则只按拼音匹配，不看上下文——如果用户说话里真的有「弓头」，会被强行改成「玄戒」。所以规则要窄（只写确定的专名），别写通用词。
* 对比热词：热词是「解码期偏置」（真的会影响声学判决），同音替换是「输出期改写」（不影响识别，只改文本）。后者更安全、可回滚，但只能修「读音完全正确、字选错」的情况；热词能修「读音也被听岔」的情况。**两者互补：离线用同音替换 + 用户可见的「原文/修正后」双栏，比热词更可控。**

### 2.3 解码参数：greedy_search vs modified_beam_search、blank_penalty、temperature

#### 支持的取值（1.13.8）

上游 `csrc/offline-recognizer.cc:36-39`：
> `decoding method, Valid values: greedy_search, modified_beam_search. modified_beam_search is applicable only for transducer models.`

流式侧 `csrc/online-recognizer.cc:116` 同样只列这两个。**`fast_beam_search` / `nbest` 是 icefall（PyTorch 训练侧）的概念，sherpa-onnx 的 C++/C API 运行时没有**；icefall 的 `fast_beam_search_one_best` / `fast_beam_search_nbest` 依赖 `k2.RnntDecodingStreams`（GPU），与本项目（纯 CPU、无 k2）无关。

**模型能力矩阵（上游 impl 构造函数里的硬编码）**：

| 模型 | 支持的 decoding_method | 证据 |
|---|---|---|
| SenseVoice（**本项目离线模式**） | **仅 `greedy_search`**，给别的值 `SHERPA_ONNX_EXIT(-1)` → **进程被杀** | `csrc/offline-recognizer-sense-voice-impl.h:77-84` |
| Paraformer | 仅 `greedy_search` | `csrc/offline-recognizer-paraformer-impl.h:94-98` |
| CTC 系 | 仅 `greedy_search` | `csrc/offline-recognizer-ctc-impl.h:182-207` |
| **Transducer**（**本项目流式模式**） | `greedy_search` + `modified_beam_search` | `csrc/online-recognizer-transducer-impl.h:110-138`、`csrc/offline-recognizer-transducer-impl.h:96-115` |

#### modified_beam_search 的收益/代价（实测数据）

| 数据集 | greedy | modified_beam_search | 速度 |
|---|---|---|---|
| Vosk 0.52 small（俄） | CER 3.64% / WER 14.53% | CER **3.50%** / WER **14.25%** | RTFx 48.2 → 29.0（1.66× 慢） |
| Vosk 0.54（俄） | CER 2.21% / WER 9.89% | CER 2.21% / WER 9.85% | RTFx 34.8 → 23.9 |
| Parakeet TDT int8 / FLEURS 英 | WER 8.50% | WER **9.04%（变差）** | RTF 0.031 → 0.029（长录音） |
| Parakeet TDT fp32 / FLEURS 英 | WER 6.03% | WER **5.85%** | — |
| Parakeet TDT fp32 / FLEURS 西 | WER 3.07% | WER 3.12%（变差） | — |

来源：<http://onlybits.org/ooobo/onnx-asr>、<https://github.com/GeiserX/akou/blob/main/docs/research/asr-benchmark.md>。

**结论：beam search 单独用（不带词表、不带 LM）收益很小甚至为负**，只有「配合热词或外部 LM」才有意义。这和 icefall 的实践一致：modified beam search 的价值在于它是 shallow fusion / LODR / contextual biasing 的载体（<https://k2-fsa.github.io/icefall/decoding-with-langugage-models/LODR.html>）。

→ 对本项目的建议：**只在「要开热词」时才切 `modified_beam_search`**；不打算开热词就保持 `greedy_search`。

#### blank_penalty

* 语义（上游 CLI 帮助原文，`csrc/offline-recognizer.cc:43-48`）：「The penalty applied on blank symbol during decoding. Note: It is a positive value. **Increasing value will lead to lower deletion at the cost of higher insertions.** Currently only applicable for transducer models.」
* 实现：`p_logit[0] -= blank_penalty_`（blank id 硬编码 0）——**加大 blank 惩罚 = 降低 blank 概率 = 少漏字、多插字**。
* Rust 字段：`OfflineRecognizerConfig.blank_penalty: f32`（`src/offline_asr.rs:567`，默认 0.0）、`OnlineRecognizerConfig.blank_penalty: f32`（`src/online_asr.rs:280`，默认 0.0）。**注意：对 SenseVoice 无效**（其解码器是 CTC greedy，不看 blank_penalty）。

本项目怎么接（只对流式）：

```rust
// 流式：模型偏「吞字」（尾部/弱音节丢字）时试 0.5~1.0
config.blank_penalty = 0.5;
```

预期收益：把「静音/轻声处丢字」换回来；代价：插入（重复字）。**必须用本项目自己的中文样本做 A/B**，因为阈值是数据集相关的。

#### temperature（temperature_scale）

* C++ 侧 `OnlineRecognizerConfig.temperature_scale` 默认 **2.0**，作用：`logit /= temperature_scale` 再 `log_softmax`（`csrc/online-transducer-modified-beam-search-decoder.cc:140-145`）。值越大分布越平（更像 beam search 的多样性），越小越尖锐（越像 greedy）。
* **Rust 绑定没有暴露这个字段**（`src/online_asr.rs:255-285` 无 `temperature_scale`），`sherpa-onnx-sys` 的 `OnlineRecognizerConfig` 也没有（`sys/src/online_asr.rs:89-121`）。→ **在本项目里改不了**，除非绕过 Rust 绑定直接调 C API（不建议）。
* `blank_penalty` 在 beam search 下是**在 log_softmax 之前**减的（`:148-151`），在 greedy 下是在 argmax 之前减的（`:126-128`）——两处语义一致。

### 2.4 端点（Endpoint）：当前实现的问题与对比

#### sherpa-onnx 的 Endpoint 机制

* C++ 类：`sherpa-onnx/csrc/endpoint.h` — `EndpointRule { must_contain_nonsilence, min_trailing_silence, min_utterance_length }` + `EndpointConfig { rule1, rule2, rule3 }` + `Endpoint::IsEndpoint(num_frames_decoded, trailing_silence_frames, frame_shift_in_seconds)`。
* 默认值（`csrc/endpoint.h:51-52`）：`rule1{false, 2.4, 0}`、`rule2{true, 1.2, 0}`、`rule3{false, 0, 20}`。
* 判定（`csrc/endpoint.cc:15-28, 76-94`）：`contain_nonsilence = utterance_length > trailing_silence`；命中条件为 `(contain_nonsilence || !rule.must_contain_nonsilence) && trailing_silence >= rule.min_trailing_silence && utterance_length >= rule.min_utterance_length`。
* 流式侧怎么算 trailing_silence（`csrc/online-recognizer-transducer-impl.h:375-389`）：
  ```cpp
  int32_t num_processed_frames = s->GetNumProcessedFrames();
  float frame_shift_in_seconds = 0.01;
  int32_t trailing_silence_frames = s->GetResult().num_trailing_blanks * 4;  // 4 = subsampling
  return endpoint_.IsEndpoint(num_processed_frames, trailing_silence_frames, 0.01f);
  ```
  → **trailing silence 是「模型连续吐 blank 的帧数」，不是「音频静音」**。模型在噪声上照样吐 blank，但在真实静音上不一定吐 blank。

#### 本项目现状与问题

现状（`src-tauri/src/asr.rs:377-381` + `:636-639` + `lib.rs:611-643`）：
* `enable_endpoint = true`，`rule1=2.4 / rule2=1.2 / rule3=20.0`（= sherpa 默认）。
* 流式链路有 **VAD 门控**：Silero 判静音 → **不把静音喂给模型** → `force_end()` 提交并 `reset()`。
* `pump()` 里每轮 decode 后检查 `is_endpoint()`，命中就 `commit()` + `reset()`。

**两个由此产生的实际问题：**

1. **`rule3`（20 秒）会硬切连续说话。** `rule3 = {must_contain_nonsilence=false, min_trailing_silence=0, min_utterance_length=20}` → 只要 `utterance_length >= 20s` 就命中（trailing_silence 条件恒真）。而 `GetNumProcessedFrames()` 在 `Reset()` 后归零（`csrc/online-stream.h:75`：「It's reset after calling Reset()」），所以是**每 20 秒切一刀**。因为 VAD 门控不喂静音，`num_trailing_blanks` 很难累计到 1.2 s，`rule1/rule2` 实际上**几乎不会触发**——真正在切句的是 VAD，而 `rule3` 在旁边偷偷切了另一刀（可能在句中切断）。**这是当前代码里最值得先修的一个点**，改一个数即可：
   ```rust
   config.rule3_min_utterance_length = 60.0; // 或 0.0(=关闭，需配合 must_contain_nonsilence 语义)
   ```
   注意：C API 用 `SHERPA_ONNX_OR(x, 20)`，所以**传 0.0 会被替换回 20**（`c-api/c-api.cc:169-170`）→ **Rust 侧无法把 rule3 设成 0**，只能设成一个更大的值（60/90）。
2. **sherpa endpoint 与 VAD 门控重复且语义不同。** VAD 看的是「音频是不是静音」，sherpa endpoint 看的是「模型是不是在吐 blank」。两者同时存在时，谁先到谁切句；VAD 通常更快（0.5 s 静音），sherpa endpoint 基本被架空。

#### 「用 endpoint 替代 VAD 门控」的可行性与风险

* **可行性：低。** 流式链路的静音段**根本不喂给模型**（`lib.rs:620-643`），sherpa 的 `num_trailing_blanks` 因此永远涨不到 1.2 s（40 帧 blank）→ `rule2` 形同虚设。要让 endpoint 生效就必须**把静音也喂进模型**，这会带来 AGENTS.md 里明确记过的坑：「否则 transducer 会在噪声上编出重复字」。
* **风险（若强行改成「喂静音 + 用 endpoint 切」）：**
  * 静音段被模型编成重复字 → 需要额外去重；
  * `rule2` 要求 `must_contain_nonsilence`（C++ 默认 true，Rust 侧**不可配置**），意味着「必须先出过字」才可能触发，空录音不会误切——这是好设计；
  * 静音时长 > rule1(2.4 s) 时会触发 rule1（`must_contain_nonsilence=false`）→ 空句提交；
  * 端点延迟从「0.5 s 静音」变成「1.2 s（rule2）/ 2.4 s（rule1）模型 blank」→ **首字与断句都变慢**，与本项目「边录边出字」的体感目标冲突。
* **结论：保留 VAD 门控为主，把 sherpa endpoint 当「兜底保险丝」（rule3 调大），不要用它替换 VAD。** 这也符合 AGENTS.md 的既有结论「流式链路带 VAD 门控」。

### 2.5 VAD 参数

Rust 字段（`src/vad.rs:12-21`）：
```rust
pub struct SileroVadModelConfig {
    pub model: Option<String>,
    pub threshold: f32,            // 语音概率阈值，越大越严格
    pub min_silence_duration: f32, // 判定静音所需的最短静音（秒）
    pub min_speech_duration: f32,  // 判定语音所需的最短语音（秒）
    pub window_size: i32,          // 帧移，Silero 必须 512 @16k
    pub max_speech_duration: f32,  // 连续语音上限（秒）
}
```
`TenVadModelConfig` 字段完全相同（`src/vad.rs:38-46`）；顶层 `VadModelConfig { silero_vad, ten_vad, sample_rate, num_threads, provider, debug }`（`:64-71`）。**1.13.8 没有 FSMN VAD**（那是 sherpa 早期的 `fsmn-vad`，现已下线）。

本项目现值（`src-tauri/src/asr.rs:69-76` 离线、`:386-393` 流式）：
`threshold=0.5, min_silence_duration=0.5, min_speech_duration=0.25, window_size=512, max_speech_duration=30（离线 MAX_SEGMENT_SECONDS）/20（流式）`。

要点：
* `max_speech_duration` **不是硬切**：sherpa 在缓冲超过该长度后把 `min_silence 0.5→0.1`、`threshold 0.5→0.9` 去逼 VAD 找静音（AGENTS.md 已记录）。所以它实际影响的是「多长还没静音就要强行切」。
* 离线模式的 VAD 切句直接决定 SenseVoice 的**逐句准确率**：切碎=每句上下文少、切长=单句过长。AGENTS.md 的实测结论是「整句一次识别最准（98.6%），切成 30 s 窗口反而 97.9%」——说明**切句是当前离线模式最大的准确率杠杆**，比解码参数更值得投入。
* `threshold` 提高 → 切得更碎/更容易漏掉轻声开头；降低 → 吃进噪声。
* 流式模式的 `min_silence_duration=0.5` 与 `lib.rs:618` 的 `700ms` 兜底窗口共同决定「静音多久算一句结束」。

**可做的实验（不写代码先能做的）**：把同一批中文样本分别用 `threshold=0.4/0.5/0.6`、`min_silence_duration=0.3/0.5/0.8` 跑一遍，比 CER。预期：切句边界对了，CER 提升 0.5–2 个点；切错则掉得更多。

### 2.7 ITN（Inverse Text Normalization）

#### SenseVoice 自带 ITN：是什么、代价多大

* SenseVoice 的 ONNX 导出里**模型自带两套 token 表**：`with_itn` 和 `without_itn`（上游 `csrc/offline-sense-voice-model.cc:123-125` 读模型 metadata 的 `with_itn` / `without_itn` id），`use_itn` 只是**选哪一套解码**。
* → **ITN 在整段模式里是「免费的」：零额外模型、零额外内存、零额外延迟**，只是换一条解码分支。
* 官方实测（sherpa 文档 `docs/source/onnx/sense-voice/code/2024-07-17.txt` 与 `2024-07-17-itn.txt`，同一个 `zh.wav`）：

  | | 输出 |
  |---|---|
  | 无 ITN | `开饭时间早上九点至下午五点` |
  | 有 ITN | `开放时间早上9点至下午5点。` |

  → ITN 同时带来：数字规范化（九→9、五→5）、标点（句末句号）、**以及同音字修正（开饭→开放）**（因为这是模型另一套输出 token，判决不同，不是纯后处理）。

* **ITN 也会出错**：同一份官方样例的英文音频，无 ITN 是 `... fifty pieces of gold`，有 ITN 变成 `... 50 pieces of code`（gold→code 错），且首字母大小写被改了。→ **ITN 是「更规整」而不是「更正确」**。

#### 流式模式（zipformer）目前没有 ITN

* 本项目流式用 `sherpa-onnx-streaming-zipformer-zh-int8-2025-06-30`，它**不输出 ITN 文本**，输出的是原始中文/数字字符。所以流式结果里「二零二五年」「三点」「百分之二十」这类不会被规整。
* sherpa-onnx 提供的补法是 `rule_fsts` / `rule_fars`（`OfflineRecognizerConfig.rule_fsts: Option<String>` / `rule_fars: Option<String>`，`src/offline_asr.rs:565-566`；流式 `src/online_asr.rs:277-278`），实现是 kaldifst 的 `TextNormalizer`（`csrc/offline-recognizer-impl.cc:913-923`：`ApplyInverseTextNormalization` → `tn->Normalize(text)`）。**对流式 transducer 同样生效**（`csrc/online-recognizer-transducer-impl.h:370`）。

#### WeTextProcessing vs SenseVoice 内置 ITN

| | SenseVoice 内置 ITN | 外挂 WeTextProcessing（`rule_fsts`） |
|---|---|---|
| 覆盖范围 | 中文数字/日期/金额/百分比/标点（模型自带规则），实测「九点→9点」 | 更全面：基数/序数、日期时间、度量单位、金额、分数、区间（`三五百→300~500`）、数学式、电话号码/车牌/身份证（`一八五四四一三九一二一→18544139121`）、IP（`幺二七点零点零点幺→127.0.0.1`） |
| 来源 | FunASR 的 `fun_text_processing`（FunTextProcessing） | `wenet-e2e/WeTextProcessing`（FunTextProcessing 的继任者，<https://github.com/wenet-e2e/WeTextProcessing>）；sherpa-onnx 通过 kaldifst `TextNormalizer` 消费其 FST 产物 |
| 成本 | **零**（模型内） | 需要生成并分发 FST 资源（几十 MB 量级）；每句文本多一次 WFST 遍历（毫秒级，可接受） |
| 风险 | 会改错（gold→code）、会改大小写 | 同样会误改（区间/电话/身份证规则容易误触发）；**与 SenseVoice 内置 ITN 叠加 = 二次规整** |
| 对本项目 | 整段模式**已经开着**（`use_itn: itn`） | **只建议给流式模式开**；整段模式**绝不能叠加**（`「15-6」`这种区间会被二次改写） |

#### 在本项目怎么接（仅流式，若要做外挂 ITN）

```rust
// src-tauri/src/asr.rs :: StreamingEngine::new()
config.rule_fsts = Some(paths.itn_fsts.clone()); // 逗号分隔多个 .far/.txt FST
// 或
config.rule_fars = Some(paths.itn_far.clone());   // fst archive
```

资源生成：WeTextProcessing 用 pynini 导出 FST → 再由 kaldifst `TextNormalizer` 打包成 `.far`。**门槛与同音替换一样高**（要 Linux + pynini），所以优先级应低于 §2.2。

**性价比判断**：流式模式里 ITN 的收益主要在「数字/日期」多不多。中文会议/评审记录里数字密度不算高，**先用一个小样本量一下「有多少句含数字」**，再决定要不要投入 ITN 资源工程。

### 2.8 标点（顺带核实）

* SenseVoice **开 ITN 时自己就输出标点**（上面 `开放时间早上9点至下午5点。` 末尾有句号），关掉 ITN 才是纯文本 → 整段模式**不要再套** CT-Transformer，否则叠成「。。」（AGENTS.md 已记录，本报告核实无误）。
* 流式模式的 CT-Transformer（`OfflinePunctuationConfig { model: OfflinePunctuationModelConfig { ct_transformer, num_threads, debug, provider } }`，`src/offline_punctuation.rs:26-56`；`OfflinePunctuation::add_punctuation(&str) -> Option<String>`）只用于**给句子定稿补标点**，partial 不加。保持现状。
* 标点模型（281 MB）对 **CER（字错率）几乎无帮助**，只影响可读性/导出体验 → 不属于「提升转写准确率」范畴。

## 3. 不建议做的（及原因）

| 不建议 | 原因（一手依据） |
|---|---|
| ❌ 给**离线 SenseVoice 引擎**设 `decoding_method = "modified_beam_search"` | `csrc/offline-recognizer-sense-voice-impl.h:77-84`：非 greedy 直接 `SHERPA_ONNX_EXIT(-1)`；`csrc/macros.h:54-59`：`SHERPA_ONNX_EXIT` = `_Exit(code)` → **不弹错误、不跑析构，整个 Tauri 进程瞬间消失** |
| ❌ 给离线 SenseVoice 引擎设 `hotwords_file` / `hotwords_score` | 上游 `Validate()` 会因「有 hotwords 但不是 modified_beam_search」返回 false → recognizer 创建失败 → 本项目引擎加载报错；而即使绕过校验，SenseVoice impl 也**根本没有 context graph**（官方文档：only transducer models support hotwords） |
| ❌ 在**离线 SenseVoice** 路径上调用 `create_stream_with_hotwords()` | 基类默认实现 `csrc/offline-recognizer-impl.h:36-40` 打印「Only transducer models support contextual biasing.」后 `SHERPA_ONNX_EXIT(-1)` → **进程被杀**。这个 API 在 SenseVoice 上不是「无效」，是「致命」 |
| ❌ 设置 `hotwords_file` 却忘了 `modeling_unit` | `csrc/utils.cc:172-180`：modeling_unit 非法 → `SHERPA_ONNX_EXIT(-1)` → **进程被杀**。本项目流式模型必须显式写 `Some("cjkchar".into())` |
| ❌ 用 `hotwords_score = 0.0` 想「关掉热词」 | `c-api/c-api.cc:173-174` + `#define SHERPA_ONNX_OR(x,y) (x ? x : y)` → 0 会被替换成 **1.5**，等于默认开启加权 |
| ❌ 把 `rule1/2/3` 设成 `0.0` 来「关闭某条规则」 | 同上，`c-api/c-api.cc:163-171` 会把 0 替换回 2.4/1.2/20 → 关不掉，只能调大 |
| ❌ 无热词也切 `modified_beam_search` | 实测收益 ≈ 0 甚至为负（Parakeet int8 FLEURS 英：greedy 8.50% → beam 9.04%），而解码慢 1.7–11×。beam 的价值在于承载热词/外部 LM |
| ❌ `max_active_paths` 调到 16/32 | 无外部 LM 时 beam 更宽几乎无收益，CPU 线性上升；上游默认 4 足够 |
| ❌ 外挂 n-gram LM（`lm_config`）给 SenseVoice 重打分 | `lm_config` 只在 transducer 的 modified beam search 路径生效；SenseVoice 直接忽略。SenseVoice 侧唯一可用的「重打分」是 `rule_fsts` 和 `hr` |
| ❌ 在整段模式（SenseVoice）里再套 CT-Transformer 标点 | SenseVoice 开 ITN 时自带标点，会叠成「。。」（AGENTS.md 已记） |
| ❌ 在整段模式里再叠一层 WeTextProcessing ITN（`rule_fsts`） | 二次规整：SenseVoice 已把「九点」变成「9点」，再过一次 WFST 可能把「15-6」「127.0.0.1」这类规则误伤；且整段模式已有 ITN，收益为零 |
| ❌ 引入 ROVER / 模型集成 / N-best 对齐 | 需要保留多路假设与对齐图 → 内存随会话增长，**破坏「内存恒定」**；CPU 翻倍；而且本项目已实测 SenseVoice 覆盖流式是 91% vs 99%，融合更差的系统没有意义 |
| ❌ 引入二遍识别（流式出字 + 结束后 SenseVoice 重跑修正） | AGENTS.md 明确：该功能已删除，别再加回来；且要保留全部音频，与「录音不限时长、内存恒定」正面冲突 |
| ❌ 引入本地 LLM 做 ASR 后纠错 | 内存 ×3、RTF 3–13× 慢（akou 实测：2.7 GB→8.1 GB，RTF 0.049→0.143~0.387）；LLM 需要完整句子，与「消费式缓冲、边录边出字」冲突；且专名优势已被热词追平（27/30 vs 28/30） |
| ❌ 换更大的模型 / 上 Qwen3-ASR | 属于「换模型」；且成本如上（akou：下载 2.55 GB、内存 +0.6 GB、RTF 3–13× 慢） |
| ❌ 改流式 200 ms 分片大小 | sherpa 特征缓冲越界会直接 abort（AGENTS.md 已踩），必须 3200 样本且只在 `is_ready()` 时 decode |
| ❌ 写 `prefer_raw_input` / `enable_padder` / `fast_beam_search` / `nbest` / `FsmnVadModelConfig` / `DecodingMethod` 枚举 / `temperature_scale` | 这些在 1.13.8 的 Rust 绑定里**不存在**，编译不过；`fast_beam_search`/`nbest` 是 icefall 训练侧（依赖 GPU k2）的概念，sherpa 运行时没有 |
| ❌ 把「关掉 VAD、让模型吃静音」当作 endpointing 改造 | AGENTS.md 已记：模型会在噪声上编出重复字；且静音不喂模型时 `num_trailing_blanks` 永远涨不到 1.2 s，sherpa endpoint 形同虚设 |
